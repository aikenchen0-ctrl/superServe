## 本轮问题与取舍

- 现状：已有点播分片、独立解码、请求取消与画像回放工具；
  缓冲适配仍是Rust模型，未与真实播放器整合。直播候选多，消费证据少。
- 理想目标：需要的内容及时播放，未消费内容少传、重复内容少存，
  消费事实可供跨域推荐评价。实际目标先限定为本机浏览器观测。
- 行动者：用户需要稳定播放与隐私边界；平台承担资源和带宽；
  维护者承担依赖与故障成本。没有用留存口号替代这些约束。
- 主要矛盾：同一未来片段既要提前到达以降低等待，又不应在用户放弃后提前传输。
  当前只提供测量和候选控制动作，尚未求出生产策略。
- 资源：既有内容哈希、HLS发布、Axum路由、正文计数和固定hls.js发布包。
- 新代价：浏览器依赖约742KB未压缩脚本、Worker、测量开销与隔离实验入口；
  无新Cargo包，不增加推荐热路径RPC。

保留三个问题，逐项推进：

1. 真实播放、取消与消费测量：本轮深入。
2. Rust直播根、互操作及房间路由：本轮只作准入探测。
3. 跨域真实推荐效用与物理扩容：继续开放，不再扩张合成模型候选。

## 已接入内容

入口为`vedioServer/crates/vs-service/examples/playback_lab.rs`，
页面及工具位于`vedioServer/labs/playback/`。它复用既有媒体路由，
不重写HLS、解码器或推荐器。

浏览器固定使用npm发布包`hls.js@1.7.4`，
发布提交`142fcab1fd0de99beafb0e1b07102ec674a9ddf9`；
下载时核对注册表SHA512，原样复制主脚本、Worker及许可证。
来源与指纹见该目录`vendor/README.md`。
早期BufferHelper的Rust移植和此次完整浏览器引擎属于两份不同证据。

Rust只监听本机，校验Host和Origin，拒绝跨站请求；内部凭证仅在进程内注入。
浏览器不获得服务令牌，也不能调用画像和推荐写接口。
嵌套分派清空外层路由扩展，避免路径参数重复提取导致500；
本轮边界测试包括正常配置、恶意Host、跨站Origin、未开放接口及16字节Range。

页面记录出帧回调、播放区间、卡顿、XHR正文与取消；
最多保存256条请求明细，超限仍累加总字节及省略数量。
本地观测不直接写入画像、学习日志或训练标签。

## 直播候选的实际反例

复用Xiu源码及官方Windows发布物，没有自行实现媒体服务器：

| 身份 | 固定记录 |
| --- | --- |
| 默认分支读取提交 | `bdc140355ee960652e40c037ae5a9a1d73aed979` |
| 官方发布标签 | `v0.14.0` |
| 标签对象 | `ac4f3d0eaddf6a9b4b9546aa3085b3e0537e9493` |
| 标签解引用提交 | `e717b3a0edbbf729940c44eb6c02caa4667edcfe` |
| 官方Windows文件 | `xiu-0.14.0-x86_64-pc-windows-msvc.exe` |
| 实际命令行版本 | `XIU 0.13.0`，与发布标签不一致 |
| 本地二进制SHA256 | `03cb12016e07a7b5499c8669b79de46e82c6b824d5bc0b83213d8ab0cf6d9ab3` |
| 源码许可证 | MIT |

GitHub API限流后，从官方发布页获取固定资产；该SHA256是本地观测指纹，
不是发布者另行签署的校验声明。当前源码与标签都有下列路径：

```text
未配置S3
  → s3_config为None
  → map(...).unwrap()
  → HLS初始化panic
```

`probe-xiu.ps1`真实推送8秒RTMP，FFmpeg退出码0，
但HLS工作线程在`protocol/hls/src/m3u8.rs:69:92`触发
`Option::unwrap()`，未得到HLS清单。日志及收据位于
`.artifacts/playback/xiu-20261107/`，两个实验进程均已清理。

因此当前选择是**不准入该默认RTMP转HLS路径**，保留源码参考，
后续先做窄修复和回归再决定是否复用。没有用虚假S3配置绕过问题，
也没有将推流成功、普通HLS或仓库的集群声明当作低延迟直播通过。
尚未运行其WHIP/WHEP、LL-HLS、房间迁移或多机扩容。

## 验证与未完成项

本轮只新增实验入口和浏览器资产，没有修改生产Rust模块及Cargo锁文件。
定向边界测试1项通过；定向Clippy零警告、Rust格式、JavaScript和两个PowerShell脚本语法通过；
Playwright完成出帧、变化像素、限速取消、恢复、停止及两种布局检查。
没有把前轮256项全工作区通过计入本轮新验证。

本轮明确保留：

- XHR取消字节受进度事件粒度限制，首帧回调不等于物理屏幕出光。
- 同机模拟限速不代表无线丢包、公网尾延迟、真机功耗或CPU/RSS。
- 没有精确的“已渲染对应编码字节”映射，不计算过拉系数或宣称三低收益。
- hls.js实验参数没有绑定既有Rust播放器票据和滞回控制。
- `no-store`用来隔离浏览器缓存，不证明CDN、对象存储或共享缓存收益。
- 推荐曝光、身份与撤回仍未打通，不自动把客户端报告当可信反馈。

回读完整带宽档案后仍采用其“下载、播放、重复、回源分别计量”的问题框架；
原档案中的百分比、固定参数及某分布下的缓存上限仍是各自场景的证据或假设，
不提升为本项目默认值。

下一步优先把**切换内容后的代次、可信播放/反馈及重复请求**接到统一冻结回放，
再比较有限预取与取消滞回。直播的HLS修复和物理集群作为独立门槛推进，
不为它们暂停真实消费链路。
