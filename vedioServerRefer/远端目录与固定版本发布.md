# 远端目录与固定版本发布

日期：2026-11-06

## 本轮问题

本地目录和固定版本发布已经具备校验边界，S3 媒体对象已经具备条件分段上传；但服务实例还不能从同一远端对象存储读取固定目录版本。若直接增加可变 `latest`，会把目录半成品、版本竞争和启动不一致引入运行路径。

本轮把问题收窄为一个协议：媒体对象必须先存在且通过长度与 SHA-256 校验，内容寻址目录用不可覆盖条件写入，最后用不可覆盖条件写入 `releases/<version>.json`。读取者只接受显式版本，不追随可变指针。

## 采用的根参考

继续采用已锁定的 OpenDAL 0.59.5 S3 适配，不复制签名、HTTP 传输器、分段上传或不安全内核：

- 参考源码提交：`532050ac3c099dd8591cde652a8ed1aaf03ba418`
- 实际发布包提交：`fce9cdefdea7c8e54dfbaf3c88c3b6d5ec68146e`
- `if_not_exists(true)` 在 S3 适配中映射为 `If-None-Match: *`。
- HEAD 返回 ETag 时，后续分块读取附带 `If-Match`，在后端遵守条件读取语义时拒绝混读其他版本。

Apache Object Store `c216edef0ac3d0d39da5bcdfeed3dcd034e26597` 继续作为源码对照。它的 `PutMode::Create` 也表达条件创建，但本轮不增加第二套运行依赖。

AWS S3 官方条件写说明在本轮用作协议约束对照：`If-None-Match` 已存在对象时返回 412；并发条件写的首个完成者胜出；`CompleteMultipartUpload` 的 409 不能按普通 Put 盲重试。具体后端仍需合约实测。

## 代码变化

- `crates/vs-service/src/s3_catalog.rs`
  - 新增有界 `S3CatalogRepository`。
  - 发布前逐媒体读取并校验长度与 SHA-256。
  - 目录按内容散列条件写入，版本记录最后条件写入。
  - 竞争时只读核对完全相同内容；异内容返回冲突。
  - 提交响应丢失时只读核对；读不到则返回 `release_may_have_committed=true`。
  - 固定版本加载校验 schema、版本、目录长度、目录散列和资产统计。
  - 使用本次 HEAD 返回的 ETag 进行条件读，最终再按发布记录校验目录散列。
- `crates/vs-service/src/publication.rs`
  - 把目录解析、版本记录构造和固定版本校验提取为远端复用的窄函数。
- `crates/vs-service/src/s3_publication.rs`
  - 抽取锁定 OpenDAL S3 Operator 构造，不复制 SDK 实现。
- `crates/vs-service/src/main.rs`
  - 增加 `VS_PUBLICATION_BACKEND=s3` 与 `VS_CATALOG_RELEASE` 的远端固定版本启动路径。
  - S3 目录和 S3 媒体必须使用同一组显式对象存储配置。
- `crates/vs-service/examples/publish_s3_catalog.rs`
  - 新增离线目录发布入口。
- `crates/vs-service/examples/s3_publication_contract.rs`
  - 增加真实 RustFS 四端点目录发布、竞争、固定版本读回及清理阶段。

  - 11 项确定性协议和进程测试。

## 配置

目录发布和远端读取共用：

```text
VS_S3_ENDPOINT
VS_S3_REGION
VS_S3_BUCKET
VS_S3_ACCESS_KEY_ID
VS_S3_SECRET_ACCESS_KEY
```

目录加载：

```text
VS_PUBLICATION_BACKEND=s3
VS_CATALOG_RELEASE=<固定版本>
VS_STORAGE=s3
```

API 角色可以只加载远端目录而不创建媒体存储；`all` 和 `media` 角色需要同时启用 S3 媒体读取。

## 未闭合边界

1. 目录发布成功不等于 Qdrant 索引就绪；当前发布收据明确不声称 `qdrant_readiness`。
2. 当前没有自动 `latest`、在线切流或 fencing；调用方必须显式选择版本。
3. 发布失败可能留下未引用目录对象，需要独立 GC；GC 必须读取版本历史和保留策略，不能按时间盲删。
4. 超时和响应丢失仍可能导致发布结果不确定；系统返回不确定状态，不盲重试或删除。
5. RustFS 验证仍为同机四进程，未验证物理故障、网络分区、跨区域、吞吐、CPU/RSS、修复和扩容收益。
6. 未完成视频编码、播放器预取、首帧、播放取消和推荐质量的联合 trace，因此不能宣称三低目标已经实现。
7. 条件写约束只保护遵循协议的写入方；受信发布者之外的覆盖或删除权限、当前版本删除标记和保留策略仍须独立控制。内容散列是完整性核对，不能替代发布者身份认证。
8. 默认两个并发操作、单次存储等待 30 秒；媒体验证按 64 KiB 顺序读取。8 MiB 目录仍完整缓冲并解析，不能把读取块大小称为总内存上限。发布重试完整读回媒体有带宽与 CPU 代价。
9. 目录发布是离线管理接口；丢弃 future 或退出进程不能撤回已发出的单次 Put，也不会返回一份最终回执。恢复时需查询固定版本或重试整个发布；本轮没有向公共 HTTP 暴露发布接口。
10. 收据中的 `catalog_created` 和 `release_created` 仅在本次收到成功写入响应时为真。响应丢失后读回相同内容也可成功，但这两个字段为假，不能据此断言对象在本次调用前已经存在。
