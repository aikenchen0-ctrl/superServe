# 媒体对象存储根项目评估

核查日期：2026-11-05。当前结论：**RustFS 是优先实验根项目，Garage 是副本型对照；生产选型和收益尚未确定。**

最新准入证据：[完整服务端回归](RustFS完整服务端回归.md) 已完成相同构建条件下的三组配对，原版 56 通过 / 4 失败，候选补丁 60 通过 / 0 失败。此前锁库 12 项取消合约通过；Linux 上游锁测试原版 135 项通过、补丁版仍有一个通知相关失败，Windows 既有截止时间失败也保留。持续取消资源上界、物理多机与生产三低收益尚未验收，继续阻断生产准入。

本文件累计记录 `Q3-storage` 的根评估与后续 S1 基础合约验证，连带核查 `Q5` 的存储扩容边界。API、跨域推荐、画像授权的主问题保持在 `问题空间.md`，不能由对象存储代替。

<重表述提示词为问题>如何复用 Rust 对象存储，在媒体不可变、按范围读取和节点可能失效的条件下，减少容量、节点间传输与读取开销，并让新增机器提供可验证的新容量，且不以更高首片延迟或丢失数据为代价？</重表述提示词为问题>

## HMM 问题对象与矛盾

| 对象 | 本轮定义 |
| --- | --- |
| S0 | 现有服务可通过 OpenDAL 读取 S3，已有同机计算副本测试和 WSL 四进程基础合约结果；没有真实多机故障、容量分布或性能结果。 |
| Sg | 选出的存储根通过同一对象/Range 合约、故障完整性和有效扩容验证；成本及边界可测，可经 S3 接口替换。 |
| IFR | 已发布媒体在需要的位置以所需字节可读，故障恢复和容量增长无需应用搬迁会话，也不反复搬运未消费的数据。 |
| 基底约束 | 容错需要独立冗余；纠删码重建消耗计算和网络；节点加入不会消除数据迁移；有限带宽、磁盘和法定人数限制可用性。 |
| 可用资源 O | 固定上游源码、现有 S3 适配、不可变对象标识、缓存、热度信息、可重建的派生媒体、独立磁盘和追加存储池。 |
| 代偿约束 | 副本空间；纠删码 CPU/跨节点扇出；元数据和锁；修复/再平衡流量；运维拓扑、版本兼容与升级成本。 |

`TC`：减少副本容量可能增加编码、重建、跨节点读取和尾延迟。增加预取或缓存可能降低等待，却占据更多网络与存储。

`PC`：同一对象为任意节点故障后立即读取，需要在多个位置具备可恢复信息；为减少存储和传输，又不希望重复保存或搬运这些信息。采用整体/部分与条件分离：完整对象与校验分片分别承担不同职责；缓存依据热度另行验证；重建只在必要时发生。选择纠删码并没有消除代价，而是把部分容量代价转换为计算、网络和调度代价。

| EAFC | 作用链与失效条件 |
| --- | --- |
| 用户、设备与服务运营者 E | 用户需要少等待、少无效下载；运营者提供盘、网络和恢复能力。 |
| 属性 A | 对象大小/热度、范围长度/位置、并发、盘容量与延迟、节点独立性、保留期和编码档位。 |
| 有用/有害功能 F | 正确范围交付与恢复；额外读放大、重试、校验片搬运、再平衡干扰和不可用。 |
| 条件 C | 故障域真实独立、对象已完整发布、元数据/锁可用、读写法定人数满足、剩余容量足以修复。 |

关键因果链：

```text
减少客户端请求范围
  AND 存储实际读取粒度/并发受控
  AND 播放器及时取消
  -> 才可能同时减少无效下载和后端工作

更少客户端字节
  不直接推出更少节点间字节或更低 CPU

新增机器
  AND 拓扑合法
  AND 故障域/容量布局允许
  AND 有效数据实际迁移或新增写入得到分配
  -> 才能证明可用容量增长

元数据不可用 OR 锁/法定人数不足 OR 必需数据不足
  -> 任一项都可能使对象不可读
```

## 根项目比较

| 维度 | RustFS 1.0.4 | Garage v2.5.0 | 对本项目的影响 |
| --- | --- | --- | --- |
| 容量机制 | 纠删码，必须按池/集合/盘确定几何与校验片数，R1/R2 | 副本；纠删码不属于项目目标，G1 | 媒体容量增长下优先测 RustFS；不能由此推断 CPU/延迟更优 |
| 最小实验 | 四节点各一盘，EC:2；数据重建门槛 2、写法定人数 3，实际读取还依赖元数据与锁 | 三节点、三副本、consistent 模式读写 quorum 2，G3 | 两种实验节点数不同，不直接比较总吞吐；真实主机故障另测 |
| 扩容方式 | 已初始化池的端点、盘数和集合宽度不可随意改变；追加新池，R1 | 更新布局并迁移；新增节点是否增加有效容量取决于区域/容量约束，G3 | “支持扩容”必须落到可用容量、迁移时间和业务干扰 |
| 小范围读取 | 需要实测分片获取、重建和并发产生的放大 | 选择重叠块、取得块流后丢弃范围前缀，G4 | OpenDAL 的 64 KiB 不是物理读取上限；不能推断固定放大倍数 |
| 条件写与发布 | R3 列出相关接口与上游测试；本地一次四端点 8 字节竞争通过，完整并发/故障语义未验 | G2 明示条件写不能安全实现并发锁定/首次写入保证 | 不把统一 S3 API 名称当相同一致性；发布真相需另验 |
| 元数据和热点 | 与锁、池和磁盘布局一起验证 | G2 指出单桶对象索引不分片；256 个分区限制布局粒度 | 热桶/多小对象值得单独测；客户端分桶会新增命名和管理代价 |
| 源码接入 | workspace 要求 Rust 1.99.0，R6；以独立服务和 S3 接口复用 | 独立服务、统一 S3 合约对照 | 当前应用 1.96.0 不随存储根升级；不复制存储内核进业务 crate |
| 本轮复用 | 已改编四节点 Compose，保留版权、许可证与改动记录 | 已克隆并作源码对照，未复制实现 | 配置可审查，内核升级边界明确 |

上游测试名称和文档是“值得验证”的证据，不是本机测试结果。Garage 的分区数量不是 256 节点硬上限，也不能据文档中的规模提示宣布它无法扩容。

## 容量取舍必须算完整

只计算理想的数据载荷冗余，不计元数据、文件系统、小对象填充、版本、临时数据和空闲保留：

```text
三副本：载荷物理空间 / 逻辑空间 = 3
纠删码 k 个数据片、m 个校验片：(k + m) / k
4 盘 EC:2：2 + 2，理想载荷系数 2
12 盘 EC:4：8 + 4，理想载荷系数 1.5
```

这不是实测容量比或可靠性等价证明。更宽的集合增加节点/磁盘参与和恢复条件；四个目录位于同一主机时不获得四个独立故障域。生产配置要按允许损失的主机/磁盘数量、修复窗口和容量增长决定，不能只选最小系数。

总存储至少包括：保留原片 + 各编码/档位派生对象 + 容错冗余 + 元数据/索引 + 缓存 + 上传/转码暂存 + 修复预留。减少原片或派生档位是独立变量，需同时评估未来重编码成本、设备兼容与可恢复性。

## 本轮决策与反例

选择 RustFS 优先进入实验，是因为纠删码及追加池路线与容量增长问题匹配，同时保留现有 OpenDAL/S3 替换边界。没有测量前，不选择其作为所有状态的存储，也不宣称它优于 Garage 的资源占用和首片延迟。

反方最强问题是：**节约下来的磁盘，是否被小 Range 的跨节点读取、CPU 和 P99 代价抵消？** 因此先测对象合约和范围工作负载，再测扩容；若读取成本或复杂度不合格，回到 Garage 副本方案或同协议的托管存储对照。增加缓存必须单独计入容量和冷启动成本，不能用暖缓存遮住存储退化。

副本型对照以至少单主机故障下的约定读写行为为共同约束。各方案实际主机数、盘数、有效容量、硬件和副本/校验参数随结果报告，不能把不等资源的总吞吐作为公平胜负。

## 实验与准入门

四节点配置已写入 `../vedioServer/labs/rustfs/compose.yaml`。本机可做协议实验，但真实多机和独立盘验证仍待环境。

| 门 | 输入与动作 | 必须记录 | 失败处理 |
| --- | --- | --- | --- |
| S0 来源与启动 | 记录提交、镜像摘要、二进制/平台和拓扑；四端点健康探测 | 版本是否对应、启动结果、每卷实际磁盘/故障域 | 来源或启动不明就停止性能结论 |
| S1 对象合约 | 合成不可压缩对象及实际编码视频；PUT、HEAD、全量 GET、单 Range、条件写竞争、重启 | 长度/散列、响应码、胜者数量、旧版本可见性；失败与重试 | 完整性/条件写失败禁止发布路径接入 |
| S2 范围代价 | 64 KiB/256 KiB/1 MiB；首部/随机偏移/跨块/尾部；冷暖缓存分开；并发逐级加压与取消 | 首字节 P50/P95/P99、CPU/RSS、请求数、交付字节、磁盘和节点间字节、取消后残余读取 | 不满足体验/资源约束则换块策略或存储分支 |

| S4 有效扩容 | 保持原池，追加新池；独立文件系统、足够非空数据，按上游流程触发再平衡 | 非零移动字节、池使用变化、明确结束状态、期间读校验及性能、完成后全量校验 | 零迁移不能算通过；恢复原服务配置或中止后按上游恢复程序处理 |
| S5 业务回放 | 固定视频/设备/播放 trace、画质和推荐候选；训练/调参集与验证集分离 | 每有效观看分钟成本、首帧/卡顿、未观看字节、覆盖和效用 | 任一体验/授权硬约束退化就回退 |

S2 的首字节不是播放器首帧。S1/S3 需要实际读写，不以健康检查代替。样本同时覆盖短小对象、长片、多档位、随机读和热点，不能只用顺序大文件或可高度压缩的零填充数据选出赢家。参数门槛由基线和业务 SLO 决定，本轮不虚填毫秒/收益百分比。

## 开发顺序与保留问题

1. **本轮已完成**：固定源码、源级比较、四节点配置改编、来源许可证记录。配置解析和缺失凭证拒绝已验证。
2. **后续已完成 S1 的健康基线**：官方 Linux 发布包经 SHA256 与自报提交核验，WSL 四进程通过直接读取和媒体 HTTP 合约。Docker 镜像仍未验证。
3. **后续已通过进程生命周期完整性**：两次正常全停重启、单进程强制退出期间的读写及重新加入后的读取；尚未覆盖主机断电或磁盘损坏。
4. **S2 已建立观测子集**：三层正文计数、GET/HEAD 和取消交换可复核；下一步对照块策略及测物理资源，S3 物理修复仍开放。小对象条件竞争不外推到 multipart 和故障竞争。自动化只操作专属实验桶、对象与已记录节点，记录失败而不静默重试到成功。
5. S4 在独立磁盘/文件系统和可测负载具备后执行；SNSD 单盘部署不作为可原地扩容起点。
6. Q2 继续确定跨域画像的证据、授权、失效与事实库；Q4 继续评估 Qdrant 召回、请求共享和学习排序。媒体对象存储不承接这些真相。

以上不是既定工期。真实负载、保留期、SLO、物理资源不足时保留候选，依问题空间更新选择。

## 实际状态

源码已克隆；四节点 Compose 解析通过；缺失凭证时拒绝配置；四个回环端口、独立命名卷、统一池布局及禁用附加协议已核查；复制的许可证与上游文本一致。

后续通过 WSL 运行官方 Linux 发布二进制完成了真实四进程基础合约：4 次直接完整读取、28 组直接 Range、48 项媒体 HTTP 检查及一次四端点 8 字节条件竞争通过。对象、临时桶与进程已清理，日志保留；本轮也重新通过了 16 项应用测试。完整结果见 `problem-space/storage-contract-evaluation.xml`。

新增恢复验证把写入和只读验证分开。两个不同内容的对象在两次正常全停重启、一次单进程强制退出及重新加入后均校验通过；七个阶段累计 26 次完整读取、182 次范围校验、312 项 HTTP 检查。缺失对象反例按预期拒绝，阶段日志和清理收据保留，见 `problem-space/storage-recovery-evaluation.xml`。

新增 S2 观测在同一适配层记录存储 HTTP 正文，实验客户端记录实际应用消费量；九个样本通过。当前 64 KiB 分块下，1 MiB 范围产生 16 次 GET，3145801 字节完整范围产生 49 次 GET；各有一次 HEAD。一次首块后取消消费 65536 字节，第二次 GET 已启动并被放弃。见 `problem-space/storage-measurement-evaluation.xml`。这明确了下一步应比较读取粒度，但不能据一次取消样本设定过拉上限，也未得到 CPU、物理流量或 P99。

Docker Linux 引擎仍未运行、镜像未核验；真实宿主断电、物理分片修复、网络分区、再平衡与性能收益仍待验证。WSL 挂载盘和文件描述符软限制也使本次结果不适合吞吐/延迟选型。

后续读取模式矩阵和两轮取消生命周期对照发现新的准入阻断：RustFS 1.0.4 在部分响应头前取消后，对象删除返回 503，服务端明确记录对象写锁获取超时。重启清理成功不能解除该阻断。当前 RustFS 仍为固定版本实验候选，生产准入暂停；不因原生流式少 GET 就推广默认模式。详见 [读取策略与取消生命周期](读取策略与取消生命周期.md)。

后续直接 S3 探针绕过媒体服务和 OpenDAL Reader，在首个 GET 响应头前取消后再次复现同类写锁超时。两轮各 20 案例，首次失败一次、独立复验通过；不能凭单轮通过解除阻断。源码疑点和完整收据见 [RustFS 取消最小复现](RustFS取消最小复现.md)。该实验阶段尚未修改或编译上游修复。

锁库实验已确认取消资源所有权缺口，候选补丁通过 12 项合约；Windows 原版与补丁版完整上游测试均 134 通过/1 失败，历史证据见 [锁取消修复实验](RustFS锁取消修复实验.md)。

最新完整 Linux 服务端配对中，原版 56 通过/4 失败，补丁版 60 通过/0 失败；Linux 上游锁测试补丁版仍有一个通知相关失败。有限样本支持候选修复，持续取消的资源上界尚未确定，详见 [完整服务端回归](RustFS完整服务端回归.md)。
