# 模型精确Top-K与召回边界

日期：2026-11-06。结论：显式新增`model-topk`，保留完整模型结果并限制选择器暂存；
不改变默认后端，不宣称减少全目录评分或普遍加速。

<重表述提示词为问题>学习模型改变候选顺序后，怎样避免旧召回截断新模型结果，并以最小新增结构控制选择成本、保持部署和权限一致？</重表述提示词为问题>

## 问题与取舍

当前状态S0：模型已纳入固定部署，但只允许全目录排序；旧分组和Qdrant标签候选与模型互斥。
理想功能IFR：当前授权范围内模型偏好的候选自然保留，用户不需要选择召回预算。
现实目标Sg：先取得精确、有界暂存的可选路径，再独立求解减少评分次数。

技术矛盾：降低候选数量能减少排序成本，却可能删掉当前模型的最佳结果。
物理矛盾：候选在新模型判断前既要被删以省成本，又要被保留以保证正确。
本轮采用时间分离：先过滤与完整评分，再按完整排序键删掉落后项。
代偿是继续扫描全部目录；没有可证明的分数上界时，不把旧标签顺序当新模型顺序。

服务维护者承担CPU、内存和部署成本；用户要求授权过滤、隐藏与拒绝标签始终生效；
评价者要求同模型、同请求、同目录对照，不能以更换评分或放宽过滤换取速度。
最小因果链为：旧分数候选裁剪 AND 模型顺序发生变化 -> 最佳结果可能不可恢复。
只更换排序器无法补回已被删除的候选。

## 服务与部署

`vs-core/src/model_top_k.rs`逐候选执行领域、隐藏、拒绝标签过滤，随后计算亲和度与模型分数。
排序键保持模型分数降序、先验降序、ID升序；不重新评分、不借助子目录修改模型绑定。
响应`considered`仍是全部合法评分候选数。

选择器最多保留2K个候选槽，K由原请求校验限制在1至50。
报告的`scored_buffer_bytes`包含选择器结构和容量槽位，
不含目录、画像、输出、分配器元数据或RSS；`peak_scored_entries`统计槽中候选高水位。

两个推荐入口共用`rank_model::recommend`。
独立实例配置：

```powershell
$env:VS_RECALL_BACKEND = 'model-topk'
$env:VS_RANK_MODEL = '<模型JSON绝对路径>'
$env:VS_RANK_MODEL_SHA256 = '<固定模型SHA256>'
```

沿用既有目录、令牌和api/all角色。没有模型时拒绝启动。
部署目标中设置`"recall":{"backend":"model-topk"}`并同时给出`rank_model_sha256`；
模型先完成校验，选择器启用后才允许绑定部署。
目标仍可选择`catalog`保留原全量模型排序；旧Grouped/Qdrant继续与模型互斥。
新枚举值会被旧二进制拒绝，升级必须协调，不能假定混用兼容。

Feed及推荐响应报告`x-recall-mode: model-topk`，指标报告相同后端和固定模型指纹。
四个独立API验证模型A/B升级、新代次回退、旧读者固定及损坏模型阻止新读者。
推荐请求未增加对象存储读取；S3仅用确定性HTTP协议夹具，非真实S3集群实验。
