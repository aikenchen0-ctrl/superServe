# Qdrant 召回集成

日期：2026-11-06。当前状态：单机真实 Qdrant 合约通过，生产准入未完成。

## HMM 问题与取舍

<重表述提示词为问题>如何在共享画像和公开目录已可用的条件下，用现成 Rust 索引减少在线排序的候选量，同时保持跨场景候选、隐藏约束及可解释的降级行为？</重表述提示词为问题>

- `S0`：已有共享画像与公开目录，全量标签排序尚未接入独立候选检索。
- `IFR`：为用户找到有用候选，只计算必要候选，不复制完整用户历史。
- `Sg`：离线构建版本索引，在线最多合并 128 个兴趣候选和 64 个先验候选后统一排序。
- `TC`：裁减候选减少排序工作，也可能降低覆盖和推荐质量。
- `PC`：候选集既要足够广以保留有用内容，又要足够小以控制请求成本。
- `O`：用离线索引与在线预算分离，复用 Qdrant 稀疏索引并保留场景先验。
- 代偿：增加索引部署、发布和一次网络请求；裁剪后质量需要单独比较。

全量目录排序保留为未启用召回时的对照；本轮不自研分布式向量库。资料中的 dense、
生成式或大模型路线继续保留，需要数据和质量基线后再承担运行成本。索引只在启用召回的
实例构建，未请求场景在先验扫描前排除，不给独立画像与媒体角色增加召回索引占用。

待办至少保留三项，本轮只深入第一项：实际索引接入与过滤；真实数据上的质量/成本比较；
画像证据与撤销；视频编码、预取和物理扩容。

## 选择与边界

Qdrant 固定参考提交为 `222b2e44ab1c3f17e8246396ead6558e45041df7`，使用官方
`1.20.0` Windows 二进制进行真实合约。官方文档和本地源码确认了稀疏向量查询、
payload 过滤、集合查询和结果融合能力；本轮只接入稀疏标签候选召回，未接入用户
向量、原始资料或生成式模型。

索引按目录 SHA-256 命名，先写入独立构建集合，内容核对后再发布目录别名。
后续就绪集成已把API查询改为固定物理集合，并在启动前全量核对发布入口和实际内容，
避免别名重绑移动旧实例。候选 payload 同时保存候选 ID、场景、标签和
目录指纹；API 收到结果后仍按画像隐藏、拒绝标签和场景做第二次过滤。

## 当前链路

```text
ProfileProjection
    -> 正向兴趣标签
    -> 有界稀疏标签查询
    -> Qdrant 候选 ID
                         \
目录场景先验轮询 ---------> 去重 -> 最终授权过滤 -> 统一排序 -> Feed
```

每次请求最多带 128 个兴趣召回维度；场景先验最多 64 个候选，按场景轮询以避免单一热门
场景占满结果。Qdrant 查询预算为 800 ms，响应体最多 256 KiB；关闭自动重试和重定向。
Qdrant 不可用时保留先验候选，仍执行画像隐藏和拒绝标签过滤，并返回 `x-recall-mode:
prior-degraded`。画像服务不可用时继续返回 503，不把过期或匿名画像用于个性化。

已提供离线发布示例：

```powershell
$env:VS_CATALOG = (Resolve-Path 'vedioServer/examples/catalog.json').Path
$env:VS_QDRANT_URL = 'http://127.0.0.1:6333'
cargo run --locked --manifest-path vedioServer/Cargo.toml -p vs-service --example publish_recall
```

启用 API 召回：

```powershell
$env:VS_QDRANT_URL = 'http://127.0.0.1:6333'
cargo run --locked --manifest-path vedioServer/Cargo.toml -p vs-service
```

受保护的 Qdrant 由环境注入 `VS_QDRANT_API_KEY`。离线发布器需要集合、载荷索引、点和别名
写权限；在线 API 只需读取，但启动校验还需固定集合信息、别名、精确计数、点和向量的读取权限。
请求协议通过现有 reqwest 调用，服务版本固定，不增加新 SDK。
没有配置 `VS_QDRANT_URL` 时维持全量目录基线；配置后只在 `/v1/feed` 启用召回，
`/v1/recommendations` 保留为外部投影的全量排序对照。

发布器验证目录原始字节 SHA-256，再从同一字节构建标签字典。已有构建集合拒绝覆盖；
失败发布保留集合供检查，不自动删库。此路径不支持原地重新导入或自动轮转。
新增就绪协议、轻量健康探针和真实重绑/篡改反例详见
[索引就绪与物理集合固定](索引就绪与物理集合固定.md)；下文55项为初次接入时的历史验证。

## 实际验证

真实合约使用官方 `qdrant-x86_64-pc-windows-msvc.zip`，版本 `1.20.0`，二进制 SHA-256：

```text
3e86f79bd516097586afb5ceacf6b843bc9e32b8e4b311d94b63a3cc11432a40
```

实验构建了 162 个公开候选，完成版本化集合和别名发布，验证：

- 冷启动先验候选 64 个。
- 写入兴趣后个性化候选 66 个，低先验兴趣候选进入统一排序。
- 隐藏候选后有效候选减少为 65 个。
- API 副本共享同一画像版本 `memory-2`。
- Qdrant 停止后降级到 64 个先验候选，隐藏候选仍未重新出现。
- 画像服务不可用时仍拒绝个性化请求。

最终全目标测试共 **55 项通过、0 失败、0 忽略**，包括真实合约；格式检查和 Clippy
零警告通过，依赖锁文件未变。协议测试另覆盖隐藏项、未发布 ID、其他场景项、重复项、
错误目录、超大合法 JSON、超过候选数量上限、重定向和请求超时。

机器可读收据见 `problem-space/qdrant-recall-contract.json`，真实测试入口为
`crates/vs-service/tests/qdrant_contract.rs`，默认被忽略，执行时通过
`VS_TEST_QDRANT_BINARY` 指定官方二进制。

执行完整验证时显式运行该合约：

```powershell
$env:VS_TEST_QDRANT_BINARY = (Resolve-Path '.artifacts/downloads/qdrant-1.20.0/extracted/qdrant.exe').Path
cargo +1.96.0 test --locked --manifest-path vedioServer/Cargo.toml --workspace --all-targets -- --include-ignored --nocapture
```

原始输出保留于 `.artifacts/recall-runs/qdrant-20261106/workspace-tests.log`，
测试直接输出的 JSON 另存为 `real-contract.json`。这些运行产物与可提交汇总收据分开保存。

首次验证先遇到夹具缺少 TLS 提供器初始化，再遇到 Windows 载荷索引路径错误。
修复测试初始化并使用规范化存储绝对路径后，真实索引合约通过；没有修改上游索引实现、
关闭载荷索引或跳过失败检查。官方 ZIP 和本地二进制散列均记录，未从发布方取得独立签名
或散列清单，因此散列用于本次运行身份追溯。

## 尚未证明

本轮没有验证 Qdrant 多节点、分片、副本、迁移、磁盘故障、自动扩容、TLS 部署和真实
网络尾延迟；也没有召回率、覆盖率、多样性、用户满意度或线上收益数据。Qdrant 只是候选
索引，不能代替画像事实库、授权服务、最终排序、视频编码或媒体存储。

默认标签稀疏召回只查询正兴趣维度，负兴趣在最终排序使用；它不是完整历史序列模型，
也不保证与全量排序的 Top-K 等价。场景轮询保障候选预算有不同来源，不保证最终列表
满足场景配额或公平性。先验遍历仍可能扫描请求场景中的多条候选，不能把 192 个排序
候选上限当成整个请求的常数计算量或固定性能收益。

后续新增 `VS_QDRANT_SCORING=signed` 实验性选项，默认仍为 `positive`。带符号召回修复
原混合兴趣反例；后续中性优先条件路又修复纯负兴趣中性遗漏，并跳过该请求的索引查询，
标记 `prior-nonpositive`，独立同分边界仍失败；详见
[召回排序目标对齐](召回排序目标对齐.md)。不配置 Qdrant 的全量基线不受该选项影响。

下一阶段使用真实候选分布和播放轨迹，对比先验、标签召回、dense 向量召回及学习排序的
召回质量和资源曲线；在质量门槛未建立前不把 Qdrant 的接入称为推荐算法完成。
