# 播放器快照与异步追加适配

日期：2026-11-06。范围：现有Rust控制器到原生播放器的本地适配边界。
本轮没有安装手机测试应用，也没有连接真实屏幕渲染回调。

<重表述提示词为问题>如何把播放器实际缓冲区间、活动变化和异步下载/追加回调接入既有Rust控制器，使区间缺口、内容切换及旧回调不会误触发取片或释放错误预算？</重表述提示词为问题>

## HMM边界与取舍

现状是服务可发布固定策略，Rust控制器可按单个连续时长决策，但尚未定义真实播放器
多个区间与异步任务如何形成这个时长。理想功能是依据已有播放器状态本地执行，
不新增逐片RPC、服务端会话表或第二个播放引擎。

本轮现实目标是`PlayerSnapshot → 连续区间交集 → 取片预留 → 下载 → 追加确认`，
取消与内容切换可隔离旧任务。三个待解问题是区间与时间线、异步预算/回调、原生绑定与渲染；
本轮深入前两项，第三项明确保留。

观看者需要连贯播放，付费者承担重复下载和内存，客户端开发者负责将选中轨道映射到同一
播放时间线，运维者需要API副本不保存客户端播放状态。
核心矛盾是数据下载后应允许使用，又不能在实际追加前被当作可播放缓冲或提前释放预算。
采用时间分离：完整下载仅允许追加，新增播放器快照确认追加后再替换预留。

`src/utils/buffer-helper.ts`区间排序和当前位置选取机制，移植到
`vs-core/src/upstream/hlsjs_buffer.rs`。本项目使用整数毫秒、合并重叠及相接区间，
不跨任何正长度缺口；进一步取所有选中音视频轨道的连续覆盖交集。
保留Apache-2.0声明和原仓库许可证，不引入JS或浏览器运行依赖。

同时回读固定Media3的`PlaybackStatsListener`，核对事件、时间线不连续与会话区分；
没有复制其统计器、自动推算观看时长或持久保存历史。
本轮网页检索没有返回正文，依据官方Git固定源码和本地合约。

## 接口与状态

`vs_core::playback_adapter::PlayerAdapter`持有现有控制器、快照版本及最多一个预留：

1. `update(snapshot, next_fragment_bytes)`核对当前代次、递增序号和单调时间；返回票据即预留预算。
2. `transfer_finished(ticket, received_bytes, outcome)`核对票据和完整长度；成功返回`ready_for_append`。
3. 下载成功后仍保留预留，`update`不能因下载完成再准入下一请求。
4. `appended(ticket, new_snapshot, next_fragment_bytes)`使用追加完成后的新播放器快照原子替换预留。
5. 隐藏、暂停和跳转返回取消票据；`change_generation`同时隔离旧快照和旧任务。
6. 网络或追加任务实际结束后确认取消/调用`release`；未确认前预留仍占预算。

票据包含本进程播放对象标识、代次、请求序号和字节数，外部无法自行构造。
两个对象即使有相同代次、序号和长度，也不能互相确认请求。
票据不支持反序列化恢复；进程重启须重建播放对象，不是跨设备能力令牌或鉴权凭据。

正在追加时发生切换，重复的“下载完成”不能解除追加任务预留；
调用方须取消追加任务并等它释放资源。旧任务确认不能释放后续新票据。
旧预留未清理会阻止新取片，这是避免跨对象超预算的代偿；适配器本身不执行网络取消或超时。

快照要求：

- 只传当前选中的必要轨道，1至8轨，每轨最多128个区间，区间使用同一播放时间线。
- 空轨道表示当前不可连续播放；不把视频和音频的不重叠部分相加。
- 最多24小时的媒体位置/会话单调时间；倒退或不连续跳转须先提升代次。
- `buffered_bytes`是调用方测得的当前压缩媒体占用，不是历史下载总和。
- `in_flight_bytes`在控制器输入中也包括下载后等待追加的数据预留。

例：当前位置1000ms，视频覆盖到2500ms，音频覆盖到2400ms，后面均有其他区间，
本地控制器只得到1400ms；不把后面的片段跨缺口累计为长缓冲。
实现使用有界区间排序，不分配整片数据，不保存观看历史；
外部对不可信JSON反序列化时仍须限制输入长度，类型本身不保证解析前内存上限。

原生接入方应在播放器串行事件线程上调用，网络与追加回调回到相同线程或受互斥保护。
完整长度检查不是内容认证，现有客户端仍须验证资产SHA256并处理解码/追加失败。
`ready_for_append`不证明可解码；`appended`不证明已经显示画面；本适配器不产生兴趣或观看事实。

## 验证与复现

新增领域合约覆盖音视频区间交集、缺口、重叠、两阶段追加、旧代次、外来票据、
取消确认、快照乱序和字节预算。独立离散时间线判定器对5120组位置/区间检查连续覆盖。

真实HTTP取消合约发布现有HLS视频片，测试端点输出首个1024字节后阻塞；
客户端隐藏并切换代次，取消后对端正文守卫释放。随后验证旧完成回调不能进入新代次。
测试故意阻塞尾部以隔离机制，不能据此推出公网或S3远端取消总会成功。
追加与播放器区间输入是合约夹具，没有伪装为手机渲染。

```powershell
cargo test --locked -p vs-core --test playback_adapter
cargo test --locked -p vs-service --test playback_adapter -- --nocapture
cargo run --locked -p vs-service --example delivery_trace -- input.mp4 2 4000
```

既有窗口探针已改用本适配器执行预留、下载和追加两阶段，实际网络读取仍核对完整散列；
区间和追加回调仍由分片时间线模型提供，JSON收据保留这一来源标记。
最终回归、请求数据和限制见`problem-space/playback-adapter-evaluation.json`。

最终50个目标、204项测试通过，0失败、0忽略，包含真实Qdrant合约；
Clippy与格式检查通过，三组HTTP实验端口已释放。没有新增Cargo依赖或改动锁文件。

本轮不修改已连接手机，不添加JNI/Swift绑定，不宣称真实屏幕首帧、卡顿或观看反馈已验证。
下一步需要在客户端播放器工程中绑定实际区间、追加和渲染事件；服务器及推荐系统继续使用
明确标记来源的观测，不能把下载成功转成用户偏好。
