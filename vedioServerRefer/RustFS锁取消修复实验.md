# RustFS 锁获取取消：确定性复现与候选修复

日期：2026-11-05。状态：实际锁模块缺陷已证实，隔离候选补丁通过取消合约；完整存储服务准入仍阻断。

后续整机验证已完成固定三组配对：原版 56 通过 / 4 失败，补丁版 60 通过 / 0 失败。Linux 上游锁测试仍有一个通知相关失败。详见 [完整服务端回归](RustFS完整服务端回归.md)；以下保留前轮锁库实验的历史结果。

## 本轮问题

<重表述提示词为问题>短视频客户端停止消费后，如何让已发出的分布式加锁请求最终释放资源，既不阻塞后续写入，又不破坏正常仲裁、持锁和故障恢复？</重表述提示词为问题>

- `IFR`：取消无用读取后，不再占用后续操作需要的锁。
- `S0`：直接 S3 取消已有一次后续 DELETE 超时；实际锁实现只有显式返回路径负责回收，获取 Future 被丢弃时缺少资源接管者。
- `PC`：业务请求应立即结束；已经发出的远端操作又必须继续被观察，才能知道是否需要释放。
- `O`：时间和所有权分离。结束业务等待，将已授予资源和未完成请求移交独立清理责任；正常成功则移交给最终 Guard。
- `Sg`：取消时的授权不遗失，正常 Guard 仍保有正确仲裁集合，清理开销可界定且真实集群回归通过。
- 代偿：取消后的 RPC 观察、解锁重试以及 Handle/Arc 持有都有开销。本轮未测吞吐、CPU、RSS 或线速字节，不把资源正确性等同于“三低”已达成。

## 实验对象与证明范围

固定源：`rustfs/rustfs@46337942d55f3a8e6a97b147ca98d9ea8115555d`，Apache-2.0。

工程 `../vedioServer/labs/rustfs-lock/` 使用 Rust 1.99，路径依赖实际完整 `rustfs-lock` 包。未重写仲裁算法。隔离源码位于 `.artifacts/labs/rustfs-lock-cancel`；固定参考副本保持干净，业务服务继续使用 Rust 1.96。

远端边界替身独立运行，授权在客户端取消后仍可发生。屏障分别控制授权前、授权后应答前；返回锁号与请求锁号不同。另以真实 `LocalClient` 验证租约确实遗留，避免只证明自造替身的行为。

源码级因果链已确认：

```text
获取 Future 被丢弃
AND 最终 Guard 尚未接管
AND（已收集的授权 OR JoinSet 中尚未消费的成功 OR 仍在途的授权）
-> 已有实现没有统一回收责任
-> 锁可以在业务等待结束后继续存在
```

真实 RemoteClient 自身还有 RPC 超时及迟到清理逻辑。因此上述算法级缺陷与 HTTP 取消反例之间仍须整机回归和事件关联，不把算法测试提升为唯一根因证明。

## 补丁与剩余风险

`LockAcquireAttempt` 从获取开始就持有 JoinSet 和已收集授权。成功、失败、超时路径显式取走资源；调用方取消时，Drop 复用现有释放重试与迟到结果清理。保存原 Tokio Handle，使 Future 在运行时上下文之外丢弃时仍可提交清理。没有新增正常路径后台任务。

剩余约束：

1. 清理依赖原运行时继续运行，进程崩溃和运行时关闭仍须租约与恢复机制。
2. 沿用的 pending 清理没有新增全局截止时间；任意永不返回的 LockClient 仍可能使后台任务长驻。真实 RPC 的超时、接纳额度和迟到清理必须联合测试。
3. 永久释放失败、网络分区、租约到期和长时间取消压力尚未由本工程验收。
4. 后续完整候选二进制已通过固定三组 S3 配对中的全部 60 项；持续压力、所有远端取消阶段和物理多机仍未验收，生产准入不因此解除。
