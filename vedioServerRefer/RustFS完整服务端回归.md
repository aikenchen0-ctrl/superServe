# RustFS 完整服务端取消回归

日期：2026-11-05。状态：候选补丁获得有限样本的整机回归支持；生产准入仍阻断。

## 本轮问题与边界

<重表述提示词为问题>获取锁取消补丁进入完整 RustFS 后，能否让短视频读取取消不再妨碍同一对象的后续删除，同时保留正常读取和清理行为？</重表述提示词为问题>

- 起始状态 `S0`：真实锁库的 12 项取消与正常路径合约已通过，但此前直接 S3 取消曾导致删除写锁超时。
- 理想解 `IFR`：用户停止消费时，无用传输和资源占用自动终止，后续工作不受旧请求影响。
- 本轮目标 `Sg`：固定源码、编译条件、探针及数据，比较完整服务端的取消与删除；不把本地 Future 释放等同于远端锁释放。
- 核心矛盾 `PC`：业务等待应立即结束，但已发出的获取请求又需要继续观察，才能回收迟到授权。
- 操作子 `O`：沿用已验证的获取期所有权保护对象，将业务等待与资源回收责任分离；本轮只验证完整服务端，不扩大补丁。
- 代偿约束：清理任务、重试和资源持有仍有成本；高取消率下是否有界，需要独立压力验证。

## 实际完成的代码

1. 新增隔离 Linux Rust 工具链、`protoc` 解包和完整服务端构建脚本。工具写入用户实验缓存，保留原版及补丁版独立二进制。
2. 探针支持显式 48 位十六进制数据种子；未提供时保持原来的独立输入。配对重放固定对象字节，不固定操作系统调度。
3. S3 运行器保存实际服务端、探针与脚本的 SHA-256；原始失败和补救清理结果分开保留。
4. 新增通知池碰撞反例，检验更强的通知隔离要求；没有修改通知实现或扩大取消补丁。

入口为 `../vedioServer/labs/rustfs-lock/` 和 `../vedioServer/labs/rustfs/run-contract.sh`。业务工作区保持 Rust 1.96，独立上游实验使用 Rust 1.99。

## 固定六轮真实 S3 对照

执行前已写入 `problem-space/storage-linux-comparison-plan.json`：三组数据，每组各跑一次原版和补丁版，顺序为原版/补丁版、补丁版/原版、原版/补丁版。两种构建完成后才启动实验。

每轮新建四个进程及临时桶，执行 20 项：首个或后续 GET、64 KiB 或 1 MiB、完整范围读取、响应头后丢弃、响应头前 0/1/4 毫秒取消。后续 GET 前先完整读取 4096 字节。所有对象均为 3,145,801 字节合成数据。

## 保留的测试失败

Linux 上游锁模块：原版 135 项通过；补丁版 134 项通过、`test_writer_notification` 失败。测试时同机存在完整服务端编译，不能据此比较延迟，失败原因尚未由本次日志完整确定。此前 Windows 两种版本共同的截止时间测试失败也保留。

独立通知反例中，不同池索引的对照通过；两个对象共享同一池索引时，本对象的 `notify_writer` 唤醒了另一对象，本对象仍等待。反例通过显式轮询固定注册顺序，不依赖睡眠或随机碰撞，也不要求禁止额外唤醒。

这是对更强隔离要求的反例。上游 `fast_lock/shard.rs` 已明确承认通知池碰撞，并用有上限的等待重试补偿，后续通知等待上限为 50 毫秒。因此它不能证明永久死锁，也未证明其为 Linux 单测失败或 S3 503 的实际原因。保留共享池的内存收益与额外等待之间的取舍，暂不重写通知模块。

机器可读证据为 `storage-linux-lock-baseline.json`、`storage-linux-lock-patched.json`、`storage-notify-pool-collision.json`。通知行为依据固定上游源码核对；本轮网页查询未返回有效正文，不宣称核验了最新上游修复。

## 评价与下一问题

现在可以确认：同一候选补丁在锁库确定性实验及本轮完整服务端配对实验中都获得支持。尚不能确认：所有取消时序均安全、该缺口是所有历史失败的唯一原因，或高取消率下后台任务和租约不会积累。未收到响应头的取消仍不等于服务端已到达某个加锁阶段。

下一轮只深入第一项，其余保持开放：

1. Q3：在固定取消压力和故障预算下，关联远端授权、回收、后台任务、租约与内存；检查停止施压后的收敛，而非仅检查客户端退出。
2. Q3/Q5：真实独立主机和磁盘上的资源、故障恢复与有效扩容；同机四进程不替代物理故障域。
3. Q2/Q4：画像证据、授权版本及撤销传播，以及跨域召回与排序质量。
4. Q1/Q3：真实设备上的编码、预取与首帧，联合测量有效观看、无效字节和尾延迟。
