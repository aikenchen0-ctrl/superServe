日期：2026-11-06。范围：受信发布者、本地文件后端、固定版本启动；不修改默认缓存开关。

## 根参考与矛盾

`S0`：缓存依赖内容不可变，但原来只有“发布者不得覆盖”的约定；目录由手工路径加载。
`IFR`：完整内容验证后才可见；同内容不重复持久化；版本变化不改写旧副本。
`PC`：发布阶段需要可变半成品，读者只能看到完整不可变结果。
按时间和位置分离：临时文件写入并验证，最终不可覆盖发布；版本记录最后提交。

本轮待办为三项，按顺序完成：媒体校验发布；目录版本提交；固定版本双副本与失败验证。
用户要求精确媒体与稳定历史，发布者要求可重试，运维者承担暂存、旧版本和孤立产物成本。
可信根目录及发布者权限属于输入边界，不把普通文件操作当作对恶意管理员的安全沙箱。

## 先验证候选假设

固定OpenDAL参考提交：
`532050ac3c099dd8591cde652a8ed1aaf03ba418`。
实际`opendal-service-fs 0.59.5`发布包记录的提交：
`fce9cdefdea7c8e54dfbaf3c88c3b6d5ec68146e`。
两者分开记录，不假定HEAD就是发布包字节。

隔离探针`fs_publication_probe`的本机结果：

- 无原子暂存目录、显式分块写入时，目标在close前已存在；writer创建本身仍是惰性的。
- 原子暂存路径中，两个写者都在最终目标不存在时开始；最终目标在close前不可见。
- 第一写者close后读到`first-value`；第二写者close也成功，最终变成`second-value`。

这证明该本机配置的写前存在性检查不能保证close时不覆盖。没有修改上游，
没有据此宣称所有文件系统、S3或其他版本都具有相同结果。
网页检索本轮未返回可用正文，使用官方固定源码和发布包实际运行补足证据。

Qdrant来源为`lib/common/common/src/fs/ops.rs`，
提交`222b2e44ab1c3f17e8246396ead6558e45041df7`。
原模块覆盖发布，本项目既有适配改用tempfile的`persist_noclobber`；本轮直接复用。
tempfile文档明确该操作不是“发布和临时路径清理一同原子完成”，可能留下临时链接。
因此只承诺本轮契约下完整数据不可覆盖可见，不宣称多文件事务、掉电或NFS安全。

## 发布结构与顺序

```text
发布根目录/
  media/<sha256>
  catalogs/<目录原始字节sha256>.json
  releases/<版本>.json
```

媒体入口：

1. 验证资产声明，固定使用64KiB读取缓冲，边复制边计算SHA256及长度。
2. 写入同目录暂存文件，任何源读取错误、长度或散列不符都不发布最终键。
3. 完整验证后刷新、同步并不可覆盖发布；并发输家完整验证赢家后可复用。
4. 已有对象损坏时拒绝，不自动覆盖“修复”。已有正确对象允许在原上传源已消失后重试。

目录入口：

1. 校验目录，并完整读取、核对其中每个资产的散列和长度。
2. 保存原始目录字节到其内容指纹键，不重新排序或重编码，以保持画像和索引的指纹语义。
3. 最后发布版本记录，包含目录指纹、字节数、资产数及总字节。
4. 相同版本相同字节可重试，不同字节拒绝重绑；并发竞争只有一个版本绑定成功。

没有版本记录的目录指纹文件不作为已发布版本加载；若只写完目录就中断，重试可完成最后一步。
版本冲突可能留下新建但没有版本引用的目录文件，当前不自动删除，避免误删被其他发布引用的对象。
崩溃也可能留下暂存文件或临时链接；垃圾回收需要后续按引用和活动发布状态设计。

## 固定版本启动

```powershell
$env:VS_PUBLICATION_ROOT = 'C:\path\to\published'
$env:VS_CATALOG_RELEASE = 'release-v1'
$env:VS_ROLE = 'all'
$env:VS_STORAGE = 'fs'
$env:VS_MEDIA_ROOT = $env:VS_PUBLICATION_ROOT
```

同时使用原来的服务密钥配置；`VS_CATALOG`不得与固定发布版本同时配置。
Media/all目前只允许fs且两个根目录必须一致；API/profile可加载固定目录，不因此自动获得媒体写权限。

启动时验证版本记录、目录指纹和统计一致性；实例不追随可变latest。新版本需要显式启动新副本，
旧副本和重启旧版本仍使用旧目录。已有画像RPC仍要求目录指纹一致，不允许新旧API随意混写事件。
Qdrant索引需按同一目录指纹单独发布和验证，目录记录尚未包含完整索引就绪证明。

这些构件可供后续发布协调器使用，目前没有实现负载均衡切流、租约、共识或旧worker fencing。
本轮两个进程共享同一本机根目录，不代表跨机共享文件系统、存储副本或自动扩容通过。

## CLI与复现

仓库根执行：

```powershell
cargo build --locked --manifest-path vedioServer/Cargo.toml -p vs-service `
  --example publish_media --example publish_catalog --example fs_publication_probe
& ./vedioServer/labs/publication/run-smoke.ps1
```

实际媒体发布参数：

```text
publish_media <已存在发布根目录> <源文件> <SHA256> <字节数> <内容类型>
publish_catalog <已存在发布根目录> <目录JSON>
```

示例仅发布174字节的合成JSON字节对象，内容类型为`application/octet-stream`，
没有伪造可播放视频。真实视频目录只需遵守同一资产协议；编码、moov、分片与首帧未在此验证。

- 配置负例使用有效发布记录，并逐项核对拒绝原因，避免因其他错误提前退出而假通过。

代偿：新对象有一次完整散列和暂存写入；已有对象重试及每次目录发布都需完整读取校验，
重复目录发布可能重复扫描大量媒体。没有缓存校验收据，也没有宣称发布吞吐或CPU收益。
暂存空间最坏随并发上传大小增长，当前离线入口由调用方限制并发，不是互联网上传网关。

只约束通过该入口的受信写者；管理员、旧写入程序或有权修改发布根目录的进程仍可破坏文件。
启动加载目录不重新哈希全部媒体，请求期HEAD仍只验证长度；因此读侧凭证、发布者隔离、
不可覆盖存储策略及后续完整性巡检依然重要。文件指纹也不提供发布者签名或真实性认证。

同目录暂存避免跨文件系统移动，但文件同步和目录同步不能代替掉电实测。
若最终发布成功后同步返回错误，结果可能已可见；应核对并重试，不删除或覆盖目标。
Windows实际运行通过，Unix条件代码本轮没有编译运行；外部替换路径的恶意竞争不在保证范围。
