# 媒体范围缓存集成

日期：2026-11-06。状态：可选Rust缓存已接入，本机HTTP合约和两轮release轨迹通过；默认关闭。

## HMM 对象与选择

`S0`：同一公开资产的重复Range和并发请求会各自回源；已有鉴权、目录、长度校验和取消许可。
`IFR`：相同不可变范围只读一次，不扩读用户未请求字节；最后消费者取消后不继续后台填充。
`Sg`：对受限小Range按需合并和缓存，大Range及原生流式直通，完整验证后才发布缓存条目。

`TC`：复用减少存储GET及正文，却增加内存与冷首块等待。
`PC`：共享填充需要完整数据，取消又要求停止；固定块容易复用，但会读取未请求区域。
本轮采用条件分离，只缓存完整精确请求范围；没有做对齐扩读、后台预取或扩大请求窗口。

行动者：用户要求权限、精确字节、快速起播和滑走即停；运维方承担内存、回源及扩容冷启动成本。
基底约束是首块等待、可用网络及实际需要的字节不能凭缓存消失；当前未知量为真实重复Range分布、
跨节点热点和用户首帧。缓存收益不能替代编码、推荐效用与播放器验证。

候选比较：

| 候选 | 本轮证据 | 选择及代偿 |
| --- | --- | --- |
| Foyer固定源码 | 策略可替换、混合缓存、权重和请求合并；取消路径通知等待者错误 | 保留完整混合缓存对照，当前不引入较宽依赖 |
| quick_cache 0.7.0 | 修改版Clock-PRO、近似S3-FIFO；权重与异步加载守卫；取消可向等待者交接 | 选当前小职责适配，关闭默认特性，仅新增3包 |
| 固定块对齐回源 | 可提高部分重叠复用 | 暂缓，需同时验证扩读、取消残余与首帧 |
| 默认直通 | 无缓存驻留、无冷填充 | 保持默认，作为相同输入的成本与语义基线 |

没有做Foyer与quick_cache的同场性能排名，也没有宣称完整实现标准S3-FIFO。
选择依据是职责匹配、依赖面和实际契约；需要磁盘缓存或更严格外部持有计量时重新评估Foyer。

网页检索及Foyer页面未返回可用正文，本轮直接克隆官方quick-cache仓库并阅读README、
Cargo声明、`sync.rs`与`sync_placeholder.rs`。固定提交、许可证、发布包指纹见
`vedioServer/THIRD_PARTY.md`和`problem-space/media-cache-evaluation.json`。

## 实际接入

缓存键包含二进制资产SHA256、目录资产长度、范围起止，不存鉴权令牌和用户画像。
每个MediaStore实例持有自己的缓存，克隆该实例共享缓存；不同存储实例不会共享条目。
相同范围可复用，部分重叠不会命中。不验证部分范围的全对象散列，依赖发布对象不可变；
同一内容寻址键若被同长度覆盖，HEAD长度检查不能发现，上传发布仍需独立保证此约束。

缓存位于媒体鉴权和目录校验之后，每次仍执行原有HEAD长度检查，不以命中绕过存在性、
权限或目录规则。HTTP的Range、HEAD、ETag、If-None-Match、If-Range、416及许可寿命保留。
命中返回Bytes的共享引用；原生流式及超过条目上限的请求继续走原流。

冷加载只在下游轮询响应体时开始，处理函数创建响应不启动GET。相同键通过库守卫合并；
加载者取消会释放存储流、加载许可并向等待者交接；取消等待者不停止仍有消费者的加载者。
没有新建后台填充任务。错误、截断及部分数据不发布，后续请求可以重新加载。

加载并发预算耗尽时直通，避免持有额外缓存填充缓冲；直通仍受媒体服务的响应体并发许可约束。
库与底层OpenDAL内部仍有各自分配和第三方不安全实现，本轮没有复制到第一方源码。

## 配置与资源口径

```powershell
$env:VS_MEDIA_CACHE_BYTES = '8388608'
$env:VS_MEDIA_CACHE_ENTRY_BYTES = '65536'
$env:VS_MEDIA_CACHE_FILLS = '4'
```

不设置或将`VS_MEDIA_CACHE_BYTES`设为0时关闭。容量为16KiB至512MiB且为4KiB倍数；
条目上限1字节至1MiB，并不得大于总容量四分之一；加载并发1至64。
范围小于4KiB仍按4KiB计权，避免微小Range造成无界条目元数据。

`/v1/metrics`新增`media_cache`，关闭时为null；包含逻辑驻留权重、索引分配、条目数、
命中、错过、合并复用、加载成功/失败/取消、活动填充与直通次数。
`reused_bytes`表示返回共享缓存缓冲的逻辑字节，不是物理网络节省。

驻留权重不是进程RSS：缓存条目元数据、存储读取缓冲、活动填充和已被淘汰但仍由响应体持有的
Bytes都需分别计入。填充缓冲受并发×条目上限约束，响应体持有受媒体并发限制；
这些约束不意味着整个进程恰好只占配置容量。每个副本独立，集群常驻和冷启动成本会随副本增加。

统一返回流保留直通流内联，避免默认路径增加一次堆分配；对应Clippy枚举大小告警有局部理由。
冷范围复制到连续BytesMut，完整后才发第一块，因此首块延迟可能增加。
不以“减少GET”推断CPU必降，也不以客户端逻辑字节推断TCP/TLS总流量。

## 合约验证

新增12项合约，最终全工作区99项、25个目标通过，0失败、0忽略；真实Qdrant、
共享画像、跨目录重放及既有读模式回归均执行，最终Clippy与fmt通过。

新验证包括：

- 冷热HTTP逐字节、状态和元数据一致；未鉴权不访问缓存，长度变化不能靠命中通过。
- 相同范围并发合并；取消等待者保留有效加载，取消加载者交接而非挂死。
- 真实HTTP取消返还媒体许可；创建但未轮询的流不发GET。
- 填充预算不足直通；流式模式保持首块与取消；错误和截断不入缓存。
- 扫描下驻留权重和条目数有界；独立存储实例不共享缓存。

这些检查证明本机协议、资源生命周期和字节契约，不证明实际视频首帧或真实多机存储修复。

## 两轮 release 结果

每轮8配置：256KiB及8MiB容量，分别运行热点、扫描、混合、超限范围；每配置64个
直通/缓存配对，采用ABBA相对顺序，无预热以保留冷加载。两轮共1024对，完整状态、
元数据与有序字节保真。资产与请求轨迹指纹一致。

两个容量下，两轮正文和GET结果相同：

| 轨迹 | 直通GET | 缓存GET | 直通存储正文 | 缓存存储正文 | 客户端字节变化 |
| --- | ---: | ---: | ---: | ---: | --- |
| 热点64次×8KiB | 64 | 1 | 524288 | 8192 | 不变 |
| 扫描64个不同4KiB | 64 | 64 | 262144 | 262144 | 不变 |
| 混合64次×4KiB | 64 | 19 | 262144 | 77824 | 不变 |
| 超限64次×128KiB | 128 | 128 | 8388608 | 8388608 | 不变 |

热点存储正文减少98.4375%，混合减少70.3125%；只属于固定合成轨迹。
扫描无字节收益且保留缓存驻留，超限直通无存储收益。两档容量也没有证明策略孰强：
当前混合工作集较小，不能据此冻结生产容量或评价真实抗扫描效果。
所有配置仍每个HTTP请求做一次HEAD；热点存储总请求为128降至65，不能写成全部请求降64倍。

第二轮256KiB容量的首个非空正文块P50：

| 轨迹 | 直通，毫秒 | 缓存，毫秒 |
| --- | ---: | ---: |
| 热点 | 0.5100 | 0.3469 |
| 扫描 | 0.5477 | 0.5474 |
| 混合 | 0.6482 | 0.4482 |
| 超限直通 | 0.8698 | 0.8944 |

保留反例：第一轮256KiB扫描首块P50为0.5659升至0.6091毫秒；第二轮热点的首个
冷请求为4.1042毫秒，后63个热请求首块P50为0.3469毫秒。冷样本只有1个，
不估计其总体分布；不能用热命中掩盖首次加载。这里测的是HTTP首个正文块，不是可解码首帧，
主机未隔离，P95/P99只是有限本机样本的描述分位数。

另有每轮一批16个客户端同范围请求：直通16GET/131072字节，缓存1GET/8192字节，
15个等待者复用，客户端均收到总计131072字节；HEAD仍为16次。
响应头由测试屏障统一释放，因此只证明合并和字节，不用于生产并发延迟结论。

进程CPU总时间约2000及1828.125毫秒，包含整轮源站、客户端、直通及缓存两路，
无法归因缓存开销。采样工作集峰值约20.9及18.9MB；第一轮原生进程峰值字段未取得，
保留null而非当作0。没有独立进程基线，不能宣布RSS或CPU收益。
