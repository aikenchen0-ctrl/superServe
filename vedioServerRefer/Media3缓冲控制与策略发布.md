# Media3缓冲控制与策略发布

日期：2026-11-06。范围：Q1的Rust本地取片控制与服务端策略发布。
本轮未连接手机播放器或采集真实渲染数据。

<重表述提示词为问题>如何复用成熟播放器的缓冲控制，在已有单档HLS和请求观测上，让客户端依据当前连续缓冲、活动状态、倍速和字节预算决定取片，同时避免每个分片都调用服务端，且不把下载当成观看事实？</重表述提示词为问题>

## HMM取舍

现状是HLS可播放、请求可归因，但实验仍按固定步骤取片，没有执行缓冲控制。
理想功能是在已有客户端反馈处完成必要决策，服务端只发布固定策略，
减少不必要的媒体请求而不额外引入逐片往返或逐用户服务端状态。
本轮现实目标是“策略发布 → 固定目录与策略指纹核对 → Rust本地控制 → 实际HLS取片”。

三个待解问题分别是控制器根项目、策略发布/本地执行边界、真实渲染/效用反馈。
本轮深入前两项；真实播放器接入、模型训练和跨机流量验证继续独立推进。

付费者承担计算和字节，观看者需要快速起播且少卡顿，客户端开发者需要可解释可移植接口，
运维者需要副本无会话迁移。硬约束是Rust业务代码、现有鉴权与固定资产、不得误标观看事实。
真实设备分布、弱网曲线、首帧SLO和业务预算仍未知。

技术矛盾是更多预取可能降低等待，也增加未观看字节及内存；
同一未来片段为避免等待需要已下载，为避免浪费又需要尚未下载。
按时间和条件分离：仅活动内容基于当前缓冲继续取片，在高水位等待、低水位恢复，
隐藏/暂停/跳转停止；码率选择和观看概率模型保留为后续问题。

## 本地控制器

`vs_core::playback::LoadControl`只保留策略和一个布尔滞回状态，不分配会话表：

- 连续缓冲低于低水位时加载；达到高水位时等待；中间区间沿用上一次状态。
- 倍速大于1时提高最低媒体时长需求，并受高水位限制。
- 首次起播、重缓冲采用不同阈值，短尾片可在已确定结束后开始，空缓冲不能开始。
- 当前有在途请求时不再准入下一片；在途预留不能充当已缓冲字节来触发起播。
- 下一完整分片必须满足“当前缓冲字节 + 在途预留 + 下一片字节 ≤ 预算”。
- 暂停、隐藏和跳转清除滞回，存在在途请求时返回取消指令；切换内容须重置或创建新控制器。

参数默认是实验值：低水位2000ms，高水位4000ms，起播1000ms，重缓冲2000ms，
压缩媒体预算8MiB。运行时不允许客户端任意扩大服务端发布参数。

从上游移植时保留大小优先分支，没有移植Android分配器、设备堆余量查询、
本地文件分支、多播放器注册表、直播偏移和预加载通路。
以整数毫秒和千分位倍速替代浮点/微秒，最低时间需求向上取整；
不宣称和上游所有边界逐比特等价。
隐藏等活动限制、完整分片字节准入、在途排他、短尾片和空缓冲保护属于本项目适配。

时间阈值在两次完整分片之间检查，真实缓冲可能跨过高水位；它不是严格的分片内时间上限。
下一片单独超过字节预算时返回`fragment_exceeds_budget`，调用方需要显式降档、重封装或调整策略，
不能静默跳过媒体。暂停后是否保留已有缓冲由播放器决定，本控制器只给出动作。

`PlaybackFeedback.buffered_media_ms`须由播放器提供当前连续可播放区间，
不能用已下载片段时长总和替代，也不能把音频与视频的非重叠区间相加。
字节预算需要播放器正确预留与释放；它不包含解码器、清单、初始化和网络栈的全部内存，
所以不是进程RSS上限。`cancel_in_flight`只是一项本地指令，不证明远端停止读取。

## 服务端发布

新增`GET/HEAD /v1/playback/policy`，仅api/all角色提供，沿用服务鉴权。
响应包含控制器版本、目录SHA256、策略内容SHA256和受限参数。
ETag由目录与策略指纹组成，支持条件读取，缓存为private，区分Authorization。

播放器经可信网关获取一次策略，核对预期目录和内容指纹后，在当前播放对象固定使用。
控制器每次决策不需要RPC，也不在API副本中保存播放会话，增加API副本不要求迁移控制器状态。
指纹用于版本与内容核对，不代替TLS、身份认证或签名。

服务端可通过启动时`VS_PLAYBACK_POLICY`配置完整JSON，例如：

```powershell
$env:VS_PLAYBACK_POLICY = '{"min_buffer_ms":2000,"max_buffer_ms":4000,"start_buffer_ms":1000,"rebuffer_ms":2000,"max_buffer_bytes":8388608}'
```

配置最多1024字节，拒绝未知字段和不合理范围，非法配置在监听前失败。
默认参数是实验基线，部署方需保证多个副本发布相同策略；
当前没有新增全局策略权威、在线自动调参或部署记录对策略的事务绑定。
当前Android/iOS客户端尚未接入此Rust模块，未构建JNI、Swift或浏览器绑定。

## 验证与测量

复用`delivery_trace`实际HTTP客户端，新增：

1. 获取一次服务策略并验证目录与指纹。
2. 依据HLS分片时间线构造零消耗的缓冲模型。
3. 由本地控制器决定是否继续请求，读取每个实际对象并核对完整长度与散列。
4. 高水位或结尾停止，记录隐藏动作；服务器和端口在实验结束时清理。

```powershell
cargo run --locked -p vs-service --example delivery_trace -- input.mp4 2 4000
```

同一8秒素材、2秒分片的真实网络请求结果：

| 高水位 | 含清单/初始化的收字节 | 请求数 | 媒体分片数 | 策略获取 | 逐片决策RPC |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2000ms | 25427 | 7 | 2 | 1 | 0 |
| 4000ms | 49737 | 9 | 4 | 1 | 0 |
| 8000ms | 97996 | 13 | 8 | 1 | 0 |

完整发布资产98408字节。8000ms实验仍可能保留极短音频尾片，控制器只是暂时等待，
未将媒体标记为已完整消费或结束。实际播放消耗缓冲后应继续调用控制器。

上述缓冲来自分片时间线模型，没有连接渲染器；下载是真实HTTP，观看和内存输入是模型。
这些数字证明控制器改变了取片行为，不是首帧、卡顿、耗电或实际用户节省率。
真实反馈和弱网下的回填策略还需要真机验证。

合约覆盖滞回、倍速、重缓冲、活动切换、在途/字节预算、短尾片、输入错误不改状态，
以及策略鉴权、目录校验、条件缓存和旧实例固定。最终结果见
`problem-space/playback-control-evaluation.json`。

最终48个目标、193项测试通过，0失败、0忽略，包含真实Qdrant回归；
Clippy及格式检查通过。三组HTTP实验端口已释放，未新增运行依赖或改动Cargo.lock。
