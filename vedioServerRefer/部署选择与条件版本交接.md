# 部署选择与条件版本交接

日期：2026-11-06。范围：离线发布者和新 API 的版本选择；不修改生产路由。

## 选型

本轮复用 OpenDAL 0.59.5 的 `FutureWrite::if_match` 示例和 S3 条件头实现，新增小范围部署适配，
没有增加运行组件、依赖或存储内核分叉。对当前单键部署选择，这是已有证据下代偿较小的候选。

Apache Object Store 的 `PutMode::Update(UpdateVersion)` 也能表达条件更新；保留源码对照，
本轮没有双客户端同场基准，不宣称哪个库普遍更快。
Qdrant 别名无法承载完整部署配置，前轮已验证它可以重绑，因此不用于本轮前版本隔离。
多键事务和分布式单写者交接若需要更强协调，再重新比较事务库与共识服务；现在不先增加新集群。

## 机制

一个部署目标包括目录版本、目录原始字节SHA-256、画像权威地址，以及
`catalog`、`grouped` 或带端点/评分模式的 `qdrant` 召回配置。记录不包含密钥。

```text
验证固定目录
  AND 验证画像权威就绪及相同目录
  AND 验证可选Qdrant的实际内容
      -> 写入不可覆盖部署记录
      -> 用前一ETag条件替换部署选择
      -> 新API凭通道与明确SHA256加载
      -> 校验依赖并复查选择
      -> 固定配置后开始监听
```

对象结构：

```text
deployments/<channel>/records/<record-sha256>.json
deployments/<channel>/active.json
```

首次写入选择用 `If-None-Match: *`，后续写入用前快照的 `If-Match`。
记录包含递增 `generation`、`operation_id`、`previous_sha256` 和目标配置。
回退旧目标也创建新代次，不把旧正文覆盖回选择键，因而遵守协议的旧ETag不能再次生效。

每次条件写只尝试一次，失败不会自动读取新ETag再写。若响应丢失，尝试只读确认当前记录；
相同记录可返回核对成功，否则保留提交不确定状态。读到其他更新也不能证明本次从未成功过。
收据的 `write_acknowledged` 表示收到写入成功响应，`reconciled_by_readback`
表示只读确认；两者不保证收据返回时仍是最新选择。

读取先通过HEAD获得长度和ETag，随后条件读正文，再验证内容寻址历史记录完全相同。
快照绑定端点、区域和桶，不能直接在另一存储配置下重用；多端点集群应各自读取本端快照，
比较相同记录指纹后再更新。ETag为后端不透明条件值，不等同于业务SHA-256。

## 代码入口

- `crates/vs-service/src/deployment.rs`：目标/记录、受限读取、先决条件、单键提交与核对。
- `crates/vs-service/examples/activate_deployment.rs`：离线激活CLI。
- `crates/vs-service/src/main.rs`：新API启动路径。
- `crates/vs-service/src/lib.rs`：绑定部署选择并在`/readyz`报告指纹与代次。
- `crates/vs-service/tests/deployment.rs`：协议、独立进程与真实Qdrant联调。
- `crates/vs-service/examples/s3_publication_contract.rs`：既有RustFS实验加入条件更新和新代次回退。

目标文件格式：

```json
{
  "catalog_version": "release-v1",
  "catalog_sha256": "<目录原始字节SHA256>",
  "profile_authority": "http://127.0.0.1:8081",
  "recall": { "backend": "grouped" }
}
```

Qdrant目标的召回字段为：

```json
{
  "backend": "qdrant",
  "endpoint": "http://127.0.0.1:6333",
  "scoring": "signed"
}
```

构建与激活，沿用已有`VS_S3_*`配置、`VS_PROFILE_AUTHORITY_TOKEN`和可选`VS_QDRANT_API_KEY`：

```powershell
cargo build --locked -p vs-service --bins --example activate_deployment
./target/debug/examples/activate_deployment.exe api none activate-001 <目标JSON文件>
./target/debug/examples/activate_deployment.exe api <前记录SHA256> activate-002 <新目标JSON文件>
```

重试使用相同操作ID、相同前记录SHA和相同目标。CLI只在当前记录确为该操作时返回核对成功；
目标已经被后续更新替代时，不自动解释为新部署。

新API使用：

```text
VS_ROLE=api
VS_DEPLOYMENT_CHANNEL=api
VS_DEPLOYMENT_SHA256=<激活收据SHA256>
VS_SERVICE_TOKEN=<服务令牌>
VS_PROFILE_AUTHORITY_TOKEN=<画像令牌>
VS_S3_* = <同一存储配置，运行时只读>
VS_QDRANT_API_KEY=<仅Qdrant目标需要>
```

本模式禁止独立设置`VS_CATALOG`、`VS_CATALOG_RELEASE`、发布根/后端、画像日志/地址、
召回后端/地址/评分，避免拼出混合版本。API加载固定目录，核对画像权威，
对Qdrant执行已有全量启动校验，监听前再检查选择指纹未变化。
嵌入库绑定快照也核对目录、画像入口、召回后端和评分配置。

旧实例不会自动移动到新选择。`/readyz`报告的是该实例加载的选择，不宣称它仍为通道最新。
外部路由需要按期望部署指纹选择实例；本轮没有接管路由或终止旧实例。

## 代偿与边界

1. 该单键条件更新只序列化部署选择，不是跨服务事务，也不提供分布式画像日志租约。
2. 画像readyz确认目录与角色/日志已启用，不能证明两个画像地址共享同一历史、
   已追平所有事件，或即时撤权连续。禁止以复制日志后同时启动两写者冒充迁移成功。
3. 先决检查后依赖可能变化，监听前复核也与开始监听之间存在时间间隔。提交和启动证据
   都是有时间边界的检查；正常画像请求继续执行目录核对，Qdrant使用既有物理集合固定。
4. 运行期间没有每请求部署控制面读取，因此新选择不能自动撤销旧实例或旧请求。
   真正切流、排空、授权撤销及单写者交接继续独立设计。
5. 默认两个本地操作许可，部署对象至多8KiB，S3单次等待最多30秒、默认调用为5秒；
   目录加载和索引校验沿用各自预算。它们不是完整激活的单一总截止时间。
6. 取消无法撤回已发出的Put，操作返回前进程退出也可能留下不确定提交或未引用尝试记录。
7. 失败或竞争留下的记录不等于已激活历史；不自动GC。读者不会完整遍历前记录链。
8. 外部管理员绕过条件写、删除选择键、恢复旧正文或破坏历史可打破单调性；
   需要权限和保留治理。不可覆盖记录和内容散列不替代发布者认证。
9. 本轮没有新增每次推荐的控制面调用，但没有实测生产CPU、带宽、尾延迟或首帧收益。
