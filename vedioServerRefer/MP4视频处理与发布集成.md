# MP4视频处理与发布集成

日期：2026-11-06。范围：Q3中的封装子问题，支持已完成上传的本地普通MP4输入。
“当前最强”只表示在本轮约束和证据下更贴合，不表示所有格式或性能指标上的全局冠军。

<重表述提示词为问题>如何复用已有Rust项目，在不引入生产转码依赖、不重写存储与目录协议的前提下，把已封存MP4变为索引前置的内容寻址资产，再用现有服务交付？</重表述提示词为问题>

## HMM问题边界

- 现状：已有目录、推荐和Range媒体服务，缺少真实视频的处理入口。
- 理想功能：已有音视频载荷尽量不变，播放器尽早取得播放索引，处理成本按文件顺序复制增长。
- 本轮目标：本地MP4经过资源预检、索引前置、内容散列和不可覆盖发布，可被推荐并经HTTP读取。
- 待解问题一：MP4容器处理根项目及边界。本轮只深入这一项。
- 待解问题二：CMAF/HLS分片、设备能力、码率档位和动态取流。
- 待解问题三：学习推荐的特征、质量目标与推荐至播放的真实联合测量。

付费者承担存储、计算和带宽；观看者需要可播放与快速响应；发布者需要失败可重试；
运维者需要资源有界、版本稳定及故障可追溯。尚无真实规模、设备覆盖、首帧SLO和成本预算。
资源来自已有发布器、Range数据面、合成测试视频以及本机独立解码工具。

主要技术矛盾：重编码可能减少播放字节，却增加CPU成本、质量损失和设备不兼容风险。
本轮采用条件分离：已经适配的编码保留，仅调整容器顺序；不适配的输入由未来独立转码链处理。
这不能代替编码优化，也不自动保证客户端实际少下载。

作用链为“封存文件 → Rust容器处理 → 内容寻址对象 → 固定目录 → 推荐媒体引用 → HTTP字节”。
成功条件是各阶段成立的AND关系；任一阶段失败均不应发布新的目录版本。
没有跨对象事务，目录失败可能留下未引用媒体对象，需后续保留及GC策略。

## 已接入接口

`vs_service::video::prepare_mp4`为离线阻塞入口，由可信发布进程调用：

1. 输入必须为已封存、不会被并发修改的普通文件；默认不超过512MiB。
2. 使用上游盒子头解析做资源预检，非媒体内容累计不超过8MiB，顶层盒子最多4096个。
3. 拒绝重复播放索引、越界及截断的盒子；内部索引的重定位复用锁定依赖。
4. 流式复制媒体范围，64KiB复制缓冲，计算输出SHA256；已有前置索引则保留完整输入字节。
5. 输出先暂存并同步，再不可覆盖提交；提供`MediaAsset`给现有本地或S3发布器。

8MiB是输入非媒体字节预算，不是整个解析过程、依赖中间对象或进程RSS的硬上限。
同长度的源文件并发改写无法靠长度检查发现；上传系统必须先封存输入，不能把仍在写入的文件交给本入口。
这只是容器处理，不验证所有采样表、每个压缩包或实际设备兼容，也不执行隐私元数据清理。
库不解码，因此不能将“容器处理成功”表达为“任意视频可播放”。

新增`publish_video`示例把单个MP4发布为一个新目录版本：

```powershell
New-Item -ItemType Directory -Path '.local/video-publication' -Force | Out-Null
cargo run --locked -p vs-service --example publish_video -- `
  '.local/video-publication' 'crates/vs-service/tests/fixtures/mp4/h264-aac-tail.mp4' `
  'video-demo-v1' 'demo-clip'
```

它不合并已有目录，仅为单视频闭环入口。失败时不覆盖版本和媒体；可能保留已经提交但未被目录引用的内容。
复用已有`publish_s3_media`即可上传处理后的文件，本轮单命令示例只覆盖本地发布。

服务启动仍使用现有配置：

```powershell
$env:VS_ROLE = 'all'
$env:VS_BIND = '127.0.0.1:8080'
$env:VS_SERVICE_TOKEN = [Guid]::NewGuid().ToString('N')
$env:VS_PUBLICATION_ROOT = (Resolve-Path '.local/video-publication').Path
$env:VS_CATALOG_RELEASE = 'video-demo-v1'
$env:VS_STORAGE = 'fs'
$env:VS_MEDIA_ROOT = $env:VS_PUBLICATION_ROOT
cargo run --locked -p vs-service
```

服务需通过可信网关访问；媒体URL中的内容散列来自命令收据，媒体鉴权仍用现有服务Bearer。
没有把服务密钥写入页面或提供给浏览器，也没有新增未经授权的公网播放入口。

## 验收与后续

Rust回归覆盖载荷保留、前置输入不变、损坏/截断/分片输入拒绝、资源预算、
不覆盖既有输出，以及真实服务进程中的推荐、鉴权、前缀Range和完整读取。
独立解码需要比较源视频与HTTP读回文件的解码帧散列，不能只调用同一处理库自证。
最终执行结果、原始日志和限制写入`problem-space/mp4-ingest-evaluation.json`。

本轮已实际运行：42个目标、172项测试通过，0失败、0忽略；包含真实Qdrant合约。
Clippy及格式检查通过。独立FFmpeg 8.0解码对照中，24个视频帧和47个音频帧记录的
时间戳、长度与SHA256逐项相同；前缀Range返回206和2070字节，完整HTTP文件散列匹配。
输出24976字节，相比源文件24984字节只少8字节填充，不作为压缩收益。
已前置输入保持字节不变并复用同一对象；真实分片MP4被拒绝，未创建对应目录版本。
测试服务进程退出，端口63666已释放。

独立对照可复跑，需先构建服务二进制和示例：

```powershell
cargo build --locked -p vs-service --bin vs-service --example publish_video
./labs/video/run-contract.ps1
```

脚本只在回环地址启动服务，结束时清理进程；收据和解码证据写入仓库根`.artifacts/video/`。
可用`-Ffmpeg`、`-Ffprobe`指定测试工具路径，工具不参与发布服务运行。

本轮没有实现在线上传API、HLS/CMAF、多码率转码、设备能力协商或播放器动态缓冲；
没有首帧P95、卡顿率、真实过拉系数、进程RSS或三低收益数据。
下一步先以分片与观看窗口为问题，不再用增加基础设施测试替代真实视频进展。
