# 多副本画像集成

日期：2026-11-05。范围：共享画像访问与独立 API 排序副本。

2026-11-06更新：新日志已保存提交时特征、目录指纹和规则版本，重放不再依赖当前目录。
旧v1日志必须以可信原目录显式迁移到新文件；当前RPC仍要求API与权威服务目录指纹一致。
以下部署和历史边界保留作前轮记录，最新证据见 [开源根选型与事件版本集成](开源根选型与事件版本集成.md)。

<重表述提示词为问题>怎样在增加 API 副本时复用同一份有效画像，保持偏好和隐藏更新可见，同时限制历史复制、内部请求及协调成本？</重表述提示词为问题>

## HMM 决策

- S0：已有单机可重放事件日志；API 各自维护画像时，偏好和隐藏列表会分裂。
- IFR：增加计算副本无需搬运用户历史，任意副本使用同一有效画像。
- Sg：独立画像服务提交事件；API 按需取得有限投影并在本地排序。
- TC：计算副本可扩容，但共享状态增加一次内部请求及状态服务依赖。
- PC：状态需要单一所有者保证提交顺序，计算又需要分散到多个节点。
- O：分离状态所有权和计算，复用 Axum、reqwest 连接池及现有日志。
- 代偿：每个 Feed 多一次 RPC，画像服务暂时单点，故障时个性化链路不可用。

用户承担偏好丢失和等待成本，维护者承担复制及运维成本。本轮只使用公开候选和合成用户。
推荐范围由可信网关传入，不等于终端授权；授权版本及撤销传播尚未实现。

待办保持四项，本轮只深入第一项：共享画像与 API 扩容；画像证据和撤销；多路召回与质量；
真实视频编码、预取及物理存储扩容。

## 路径取舍

| 路径 | 收益 | 代价及决定 |
| --- | --- | --- |
| 各 API 复制事件及画像 | 本地读取快 | 增加复制、重放和失效传播；本轮不采用 |
| 多副本共同写本地文件 | 部署表面简单 | 文件不提供多机一致性；排除 |
| 共享画像服务、API 本地排序 | API 无需导入历史，复用现有 Rust 代码 | 多一次 RPC、写入端单点；本轮采用 |
| 分布式数据库或共识日志 | 可进一步解决高可用 | 新增集群及运维；未在本轮集成 |

没有增加本地投影缓存，以保持确认写入后的隐藏更新可见。三低目标落实为有限投影、
连接复用、并发及时间预算；尚未取得生产带宽、CPU 或延迟收益比例。

## 运行配置

先构建，以下在仓库根目录执行：

```powershell
cargo +1.96.0 build --locked --manifest-path vedioServer/Cargo.toml -p vs-service
```

分别在三个终端启动进程，均使用同一 VS_CATALOG 文件。DEMO_PROFILE_TOKEN 与 DEMO_API_TOKEN
由部署环境提供，至少 32 个可打印 ASCII 字符。画像服务与 API 使用不同密钥。

画像服务：

```powershell
$env:VS_ROLE = 'profile'
$env:VS_BIND = '127.0.0.1:8090'
$env:VS_CATALOG = (Resolve-Path 'vedioServer/examples/catalog.json').Path
$env:VS_SERVICE_TOKEN = $env:DEMO_PROFILE_TOKEN
$env:VS_PROFILE_EVENT_LOG = Join-Path $PWD.Path '.artifacts/shared-profile/events.jsonl'
Remove-Item Env:VS_PROFILE_AUTHORITY_URL -ErrorAction SilentlyContinue
& ./vedioServer/target/debug/vs-service.exe
```

API A：

```powershell
$env:VS_ROLE = 'api'
$env:VS_BIND = '127.0.0.1:8081'
$env:VS_CATALOG = (Resolve-Path 'vedioServer/examples/catalog.json').Path
$env:VS_SERVICE_TOKEN = $env:DEMO_API_TOKEN
$env:VS_PROFILE_AUTHORITY_URL = 'http://127.0.0.1:8090'
$env:VS_PROFILE_AUTHORITY_TOKEN = $env:DEMO_PROFILE_TOKEN
Remove-Item Env:VS_PROFILE_EVENT_LOG -ErrorAction SilentlyContinue
& ./vedioServer/target/debug/vs-service.exe
```

API B 使用 A 的配置，将 VS_BIND 改为 127.0.0.1:8082。跨机器时将画像地址改成实际
服务地址，并配置 HTTPS 或受保护的内部传输。Media 角色不持有画像日志。

使用原有 POST /v1/profile/events 从 A 写入，再向 B 的 POST /v1/feed 提交同一主体。
两端会使用相同的画像版本；已有公共 API 的请求结构不变。

## 验证与边界

真实进程测试 shared_profiles.rs 验证：A 写入后 B 读取同一画像；重复提交不重复加权；
隐藏更新跨副本可见；新增 C 无需导入历史；错误内部密钥和缺失目录指纹被拒绝；
目录漂移返回 409；画像服务停止后 Feed、写入及就绪检查不可用；日志重启后恢复且去重有效。
协议测试覆盖串用户投影、超过 64 KiB 的合法 JSON、错误响应目录和重定向。

这些是同机独立进程结果，未验证物理网络分区、TLS 部署、吞吐、自动故障转移或推荐质量。
前轮日志按当前候选标签重放的缺口已由v2冻结事实修复。每个运行实例仍固定目录快照；
重启式跨目录和回退已验证，在线协调及跨机切流尚未完成。
profile 角色必须使用本地日志；API 远端模式与本地日志互斥。单写者高可用、分片、
日志轮转和授权撤销继续保持未决。
