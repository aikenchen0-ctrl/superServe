# 画像历史水位与停写交接

日期：2026-11-06。范围：已有Rust单写者画像日志、历史前缀验证及停写转移。

<重表述提示词为问题>怎样让目标画像权威证明它包含指定已提交历史，阻止空历史或分叉历史被当作同一权威使用，并避免正常推荐反复读取全部日志？</重表述提示词为问题>

## 当前选择

继续复用已改编的cqrs事件信封、既有文件锁/同步/重放、SHA-256，以及Qdrant派生的
`atomic_create`。本轮没有加入新数据库、消息集群或依赖，没有自行实现分布式共识。
NATS JetStream保留为后续共享事件权威候选；序号或消费水位本身不能证明本地日志内容相同，
因此本轮先建立可迁移、可反驳的历史内容契约。

取舍是时间分离：重放时累计日志散列，append完成同步后只更新新字节；首次核对旧前缀时
扫描该前缀，后续请求只带短凭据。停写转移把最终水位固定下来，代价是服务间断。

维护队列：

1. 本轮：历史前缀、停写封存和部署绑定。
2. 后续：共享事件权威、跨机旧写者隔离与日志分片。
3. 后续：撤权水位、路由排空、保留和GC。
4. 后续：真实播放/推荐联合trace与物理扩容。

## 水位与请求契约

`ProfileHistoryCheckpoint`包含：

```json
{
  "schema": "profile-history-checkpoint-v1",
  "projection_version": "tag-additive-v1",
  "records": 2,
  "bytes": 746,
  "sha256": "<完整记录字节及换行的SHA256>"
}
```

记录数、字节数和散列共同约束日志；相同记录数不证明内容相同。
散列覆盖原始v2日志字节和换行，既有日志不重写、不增加逐条存储字段。
相同语义但不同字节序列会视为不同历史，后续做压缩/分段必须显式迁移此契约。

受保护接口`POST /internal/v1/profile/history`接受：

```json
{ "minimum": null }
```

或`{"minimum": <上述水位对象>}`。接口返回当前持久水位和一个已验证前缀的
64字符`guard`。核对与投影更新共用读写锁，磁盘读取在有界阻塞任务中完成；
校验任务持有许可和锁，取消HTTP等待不提前释放这些资源。

服务端验证指定前缀的长度、换行边界、记录数和散列；目标可以有后续追加，但不能缺失或
改变该前缀。每个日志最多缓存32个已验证前缀，失败证明不占槽；满后明确拒绝新注册。
此缓存非持久，画像进程重启后由启动/健康检查重新证明并注册。

新部署记录增加可选`profile_checkpoint`，新激活会写入当前已验证水位。
API启动时绑定该水位，后续画像事件和投影请求携带`x-profile-history-guard`，
服务端必须已注册且响应回显相同凭据。读取到同地址的另一空日志时，会拒绝使用。
凭据只用于内容前缀一致性，不包含令牌，也不是签名或身份认证。
API认证、目录指纹、主体/场景验证和原有画像过滤继续执行。

正常Feed没有新增独立历史RPC，也不扫描日志；事件响应仍需同步落盘，再更新增量散列。
`/readyz`在绑定水位时增加一次前缀确认请求；已注册前缀不重新扫描历史。
本地日志忙时，水位读取在持有预算的阻塞任务中等待，不在异步执行器线程等待磁盘锁；
超过并发预算时拒绝新任务。

## 停写转移

离线入口：

```powershell
cargo build --locked -p vs-service --bins --example handoff_profile_log
./target/debug/examples/handoff_profile_log.exe <停写源日志> <不存在的目标日志> <目录SHA256>
```

工具要求源为普通文件、目标不存在且父目录存在，源没有活动写者。
它执行：

1. 用既有独占文件锁持有源日志，严格验证记录和投影重放；未完成尾部不自动修复。
2. 同步源文件，计算最终水位。
3. 不可覆盖发布`<源日志>.sealed.json`，绑定最终水位和规范化目标路径。
4. 按64KiB缓冲复制，核对源散列并不可覆盖发布目标。
5. 返回`ProfileHistoryHandoff`，其中`checkpoint`用于后续部署。

遵循本版本协议的源进程检测到封存记录后拒绝重新作为写者启动。
封存成功但目标发布失败时，源仍封存；核对后只允许向同一个缺失目标继续操作，
不能借同一源转出第二个独立目标。目标已存在时不覆盖，需要独立核对。
目标日志本身不带源封存标记，可在启动重放后继续追加并接受旧水位前缀。

封存记录与目标发布不是跨文件事务。先封存是为了失败时保守停写，不能据此宣称零停机。
封存文件必须与源一起保留，不应删掉它来恢复旧写者。

## 绑定最终水位

部署激活时，新目标必须证明包含前一部署已知水位。若修改画像权威地址，还必须显式提供
`profile_minimum`，推荐取自停写工具回执的`checkpoint`：

```json
{
  "catalog_version": "release-v2",
  "catalog_sha256": "<目标目录SHA256>",
  "profile_authority": "http://127.0.0.1:8082",
  "profile_minimum": {
    "schema": "profile-history-checkpoint-v1",
    "projection_version": "tag-additive-v1",
    "records": 2,
    "bytes": 746,
    "sha256": "<停写回执中的最终日志SHA256>"
  },
  "recall": { "backend": "grouped" }
}
```

不能用初次部署时的旧水位代替最终水位：初次激活后可能已有新用户事件。
代码要求显式最低水位并校验前缀，但不能远程证明操作者提供的是源最终水位；
停写、最终回执和源封存保留仍是操作边界。地址未改变也可主动提供`profile_minimum`。

示例流程：

1. 停止并排空旧画像写者，保持源日志与封存状态可核对。
2. 执行离线转移，使用回执水位启动并验证目标画像服务。
3. 将最终水位写入新部署目标，按前部署指纹条件激活。
4. 启动指定新部署指纹的API，再由外部路由交接流量。

本轮工具复制的是调用主机可见的文件路径；可写入已挂载目标，但没有实现网络复制、
跨机锁、网络文件系统语义或云存储迁移。跨物理主机方案必须另做故障域和写者隔离验证。

## 未闭合边界

- 内容指纹证明历史前缀，不是唯一权威身份。两个空日志水位必然相同；
  两个完整复制后继续分叉的写者也共享旧前缀，本轮不提供共识或分布式租约。
- 已绑定水位只证明最低前缀，不能自动发现它之后丢失的所有事件。
  最终停写水位由操作者正确提供；旧客户端/旧部署未绑定guard时没有新增防护。
- 旧部署记录没有`profile_checkpoint`时仍可读取；需要重新激活后才能得到新水位保护。
  新字段会被旧版本严格反序列化器拒绝，需协调升级，不支持旧二进制混合读取新记录。
- 文件锁与封存针对遵守协议的路径和写者；旁路写入、删除/移动封存记录、
  别名路径/硬链接、强制恢复旧副本和不遵守锁的进程不被隔离。
- guard缓存只按受信追加式日志使用，运行期间外部原地修改文件不会被每请求重算检测。
  缓存最多32条且重启清空；容量管理、持久注册和退役策略需后续完善。
- 首次前缀核对最多扫描32MiB并阻塞同一画像投影提交；当前不是无停机迁移。
  启动与转移沿用已有全日志重放内存代价，没有宣称内存、存储或CPU普遍下降。
- 撤权水位、共享事件权威、跨机写者隔离、日志分片/压缩、路由排空、
  物理故障/扩容和真实播放推荐三低收益继续开放。
