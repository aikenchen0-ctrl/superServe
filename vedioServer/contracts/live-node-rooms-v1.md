# 有界多房间媒体节点契约

2026-11-07，v1。Web、Android、iOS共用HTTP和SDP契约；
当前验证环境仍为回环Chrome实验，尚未接通原生或公网入口。

## 配置

新入口为`VS_LIVE_ROOMS_CONFIG`，与`VS_LIVE_ACCESS_CONFIG`互斥，
并要求配置`VS_LIVE_ROOM_CONTROL_CONFIG`。旧单房间配置和根路径继续兼容。
配置文件上限16KiB；未知字段、重复房间和超限房间拒绝启动。

```json
{
  "issuer": "https://issuer.example",
  "audience": "live",
  "node_id": "media-a",
  "keys": [{"kid": "key", "public_key": "<Ed25519公钥的Base64URL>"}],
  "rooms": [
    {"tenant_id": "tenant-a", "room_id": "room"},
    {"tenant_id": "tenant-b", "room_id": "room"}
  ]
}
```

房间名册在启动时固定，数量1至8。标识限制沿用直播凭据规则：
1至64字节的ASCII字母、数字、下划线、短横线、点；
作为路径段时另拒绝`.`和`..`。不接受路径分隔符或百分号转义。
未知房间请求不创建媒体状态，不支持运行时增删名册。

多节点部署可选择协调配置`media_control.dynamic_nodes=true`及空`endpoints`。
此模式下协调Raft状态机持久维护节点目标、loopback媒体控制地址、
该节点允许承载的房间范围和登记revision。房间分配须匹配已登记启动代次
及已声明范围；旧配置省略此字段仍按静态名册工作。
动态标记参与既有协调策略指纹。不得在运行中的旧持久数据库上静默切换；
已有历史需按显式迁移流程处理。

可信部署控制器在同一service token边界内使用：

- `POST /v1/media-nodes/commands`执行`register_media`或`remove_media`。
- `GET /v1/media-nodes/{node_id}`执行线性一致查询。

登记包含带期望revision的节点代次、回环控制地址和1至8个房间范围。
每条变化均追加到Raft并复制到redb快照。节点加入或重新登记不需重启协调节点。
相同操作幂等；过期revision、重复控制地址、越权范围和超过64个登记槽拒绝。
节点只要仍被一个房间记录引用，就不能改址、换代次或删除。
先排空释放全部房间，才能移除登记；移除留下revision墓碑，禁止旧登记复活。

这仍是本机回环实验协议：服务端拒绝非loopback登记与监听地址。
它证明新增同机媒体进程可在线加入协调集群，不是公网/物理多机准入。
登记没有TTL/自动故障转移。进程失联时保留所有权并阻止释放；旧媒体不确定是否停流时
不得通过过期时间猜测停流。需要恢复时，仍须先确认旧节点排空或完成独立故障处理。

所有房间共享节点标识、128位启动代次、公钥材料及总计4个验签许可。
房间仍独立校验租户、房间、角色、分配版本、主体和授权期限；
增加房间不会把阻塞验签并发从4放大成32。

## 接入与控制

每个房间路径为`/live/{tenant}/{room}`：

- 实验页面：`/live/{tenant}/{room}/`，末尾斜杠为规范入口。
- 发布：`POST /live/{tenant}/{room}/whip`。
- 订阅：`POST /live/{tenant}/{room}/whep`。
- 创建响应中的Location包含完整房间路径。
- 会话查询、删除和续权使用该Location及其`/renew`扩展。
- 房间观测：`/live/{tenant}/{room}/lab/metrics`与`/lab/node`。

既有单房间的原始SDP、凭据、续权和音视频限制保持。
带凭据的房间不开放匿名JSON协商和删除入口。
新多房间模式没有根`/whip`、`/whep`或默认房间回退。
对照[live-sdp-http-v1](live-sdp-http-v1.md)，这仍是有限接入子集。

节点根入口`GET /lab/rooms`要求内部控制凭据，返回固定名册、
各房间状态和共享工作器状态。不会向普通客户端提供所有房间目录。
内部根`/admin/room/activate`、`drain`和`revoke-token`保持不变；
先鉴权，再按正文完整`tenant_id + room_id`选择房间，
随后校验cluster、node、incarnation和revision。未知房间404，身份冲突409。
房间前缀下的控制入口同样只能操作该前缀对应的房间。

协调服务仍使用`node_id -> 固定地址`，向根排空入口发送完整MediaFence。
无需每房间另开HTTP端口，不改变Raft状态结构或已持久化策略。
房间排空只清除目标房间，收到准确回执后才提交Release。
完整顺序见[room-handoff-v1](room-handoff-v1.md)。

## 工作器与资源

单节点一条媒体线程、一个UDP socket；每房间一个状态槽位、
4条命令队列、独立Rtc集合、音视频队列、撤权表和排空下界。
每轮每房间最多取一条命令，轮换处理起点；UDP通过str0m会话匹配归属房间。
上限8房间，每房间一发布者及两观看者，最多24条Rtc会话。
24为代码准入上限，本轮未作24连接性能认证。

每房间视频队列最多8帧、每帧256KiB，音频队列最多16包、每包1KiB。
8房间的应用层排队正文上限为16MiB加128KiB；
不包含对象元数据、Rtc协议/重传缓冲、线程栈、分配器或RSS。
撤权记录各房间最多同时64条，沿用到期回收和不可回退时间水位。

空房间保留槽位、时间水位和排空版本下界。
不按空闲、LRU或缓存淘汰销毁这些状态，避免旧分配重新激活。
进程重启统一换启动代次并关闭所有房间接入，必须重新取得权威分配。
关闭节点会停止所有房间并回收共享socket。

工作器层统计总入站UDP正文、未归属正文、超大包及共享socket反馈错误；
房间入站计数仅包含匹配该房间会话的数据。
共享socket上的ICMP不能可靠归属房间，不用于关闭任意房间。
这次变化收窄了原单房间入站/协议错误计数的含义，消费者不能把未知包算入房间。
所有这些计数均不是包含IP、UDP等头部的线路流量。

## 代偿与验收边界

共享工作器减少按房间增长的线程和端口，但扩大单工作器故障影响范围。
轮转按命令数量分配机会，不是CPU时间抢占；昂贵协商仍可能影响其他房间尾延迟。
活动状态的socket读取等待上限10ms，空房间等待上限50ms，
这是一项延迟/唤醒开销折中，尚未证明总体CPU收益。
不宣称三低收益、跨候选性能最强或单房间无限扩容。

本契约不提供动态房间名册、跨工作器迁移、跨节点媒体级联、
TURN/ICE重启、自动失联抢占、生产身份发行或TLS/mTLS。
横向扩容仍由控制面给不同节点分配房间；上线新节点的策略更新与物理多机验收未完成。
Android/iOS真机、弱网、音画同步、存储修复扩容及推荐/预取联合收益独立验收。
