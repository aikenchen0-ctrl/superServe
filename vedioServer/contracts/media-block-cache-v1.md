# 媒体单块范围缓存

## 可选策略

缓存继续默认关闭；启用缓存后原默认仍为`exact`。
显式`block-64k`和`block-64k-stream`用于同一内容对象内相邻或重叠短读的实验。
它只改变媒体节点的回源缓存粒度，不改变客户端请求范围、授权、返回元数据或内容版本。

```powershell
$env:VS_MEDIA_CACHE_BYTES = '8388608'
$env:VS_MEDIA_CACHE_ENTRY_BYTES = '65536'
$env:VS_MEDIA_CACHE_FILLS = '4'
$env:VS_MEDIA_CACHE_POLICY = 'block-64k'
```

可选值仅为`exact`、`block-64k`和`block-64k-stream`，未知值或无效编码拒绝启动。
块模式要求缓存容量非零、条目预算至少64KiB；
原条目预算不超过总容量四分之一的规则仍有效，因此至少需要256KiB总容量。
原`with_media_cache`接口沿用精确范围；
Rust调用方使用`with_media_cache_policy(config, MediaCachePolicy::Block64Kib)`显式选择。

## 读取与缓存键

原始请求先验证内容散列、声明对象长度和合法范围。
符合条目预算且未选择`stream`读取模式时，再进行以下映射：

1. 若范围完全落在一个64KiB块中，将缓存键范围扩为该块，末块裁剪到对象声明长度。
2. 若范围跨块，继续使用原精确范围键，不把它拆成多次读取。
3. 超过条目预算或`stream`模式时，继续按原范围直读。

缓存键始终包含内容散列、声明长度和有效范围，不能只使用对象名或起始位置。
客户端正文只返回原请求切片；HTTP长度、Content-Range、ETag、鉴权、
条件请求和每次对象元数据检查继续由既有媒体路由执行。
内部读取范围扩大不意味着客户端拥有访问额外字节的权限。

当前仅服务已发布的内容寻址对象。假设对象不可覆盖；完整收到指定范围的长度
不等于对部分内容重新计算SHA256，更不证明源数据在期间没有被旁路修改。
原元数据不符时的503拒绝边界保持。

## 成熟机制复用

继续使用锁定`quick_cache 0.7.0`的加权条目和异步加载守卫。
同一块的不同请求也使用同一守卫；等待者取消不会取消加载者，
加载者取消后由库唤醒等待者接续填充。
没有另建单飞状态表、后台任务或跨节点协调。

数据完整收到并校验范围长度后才插入缓存。
失败、截断或超长正文不生成条目；首个未轮询响应不会预取。
加载并发预算满时释放加载守卫，按该客户端的**原始范围**直读，
不能把扩大的块范围直接转发给客户端。

完整块通过锁定`bytes 1.12.1`的切片复用内存。
返回8KiB切片仍可能持有64KiB底层分配；条目被逐出后，
正在发送的切片仍可能使底层内存存活。
权重、索引分配和加载并发不是进程RSS或所有存活正文的严格上限。
不同媒体进程和不同`MediaStore`各自持有缓存；新增节点不会共享已热内容。

## 指标解释

`media_cache.policy`报告实际策略。
新增计数：

| 字段 | 口径 |
| --- | --- |
| `block_lookups` | 在响应正文实际被轮询后，映射到单块键的读取次数；包括随后因预算饱和直读的尝试 |
| `crossing_block_fallbacks` | 进入缓存路径但跨块、回退原精确键的次数 |
| `requested_body_bytes` | 进入缓存路径并被轮询的原始请求字节之和；含取消和失败，不是已发送正文 |
| `fill_range_bytes` | 实际开始填充时申请的范围长度之和，含取消与失败 |
| `fill_received_bytes` | 加载缓冲从OpenDAL流收到的正文之和，含失败前已收到部分 |
| `extra_fill_range_bytes` | 每个填充范围减其发起请求范围的差额之和，不代表最终未使用或线路浪费 |
| `early_yielded_bytes` | 流式填充在完整校验前向调用方产出的请求前缀之和；包括随后失败或取消，不是客户端实际收到或成功解码的字节 |

`reused_bytes`继续按实际原请求长度计，不按整块重复计量。
直读、HTTP头、TLS、重传和对象存储内部读取不包含在新增填充指标中。
源站HTTP产出、存储传输观测和客户端正文应分别保留，不能相互替代。

## 评估与复算

`media_block_cache_trace`复用现有带S3签名的确定性HTTP源站夹具，
比较直接读取、精确范围缓存和块缓存。
固定轨迹包括邻近热读、单次冷读、分散冷读、跨块、短尾块和超限直读，
在相反的变体顺序下执行，核对全部客户端正文与范围元数据。

```powershell
cargo run --offline --locked -p vs-service --example media_block_cache_trace
```

当前输出`media-block-cache-trace-v2`，比较直读、精确、缓冲块和流式块四种路径；
历史三路径`v1`报告保留，保存新报告时不覆盖旧证据。
该入口可使用debug执行，比较正确性、GET数量和正文计数；
不根据调试耗时排名CPU、延迟、功耗或生产容量。
源站是协议夹具，不是RustFS真实集群或物理多机。

既有默认配置和精确模式继续保留。邻近热读可能节省回源，
单次冷读或分散读取可能将8KiB需求扩大到64KiB。
缓冲式`block-64k`会等待更多数据再交付首个切片；起播、取消及总体收益需真实负载验证。
没有默认开启或自动策略识别，也没有跨节点缓存和扩容收益声明。

## 显式流式块候选

`VS_MEDIA_CACHE_POLICY=block-64k-stream`采用相同的键、范围、容量和加载并发限制。
只在原本有资格填充的冷请求中，使用OpenDAL不设chunk的读取，
复用锁定`async-stream 0.3.6`的`stream!`，将借用缓存的quick-cache加载守卫保留在响应流内。
未轮询响应不启动GET；没有另建线程、后台填充任务、通道队列或单飞状态表。
原生`VS_MEDIA_READ_MODE=stream`仍优先按原范围绕过缓存；
预算满、超限的请求仍使用原读取模式按原范围直读。

加载者每次只转发当前源块与原请求的交集，其他字节只进入有界块缓冲。
完整块结束并检查长度后，才发布条目和交付原请求最后一个字节。
保留此字节，是为了防止HTTP按Content-Length提前认为响应完成并丢弃未校验的块尾，
也使尾部失败不能呈现为一个完整成功响应。已经交付的前缀不能撤回；
错误通过未完成正文体现，不保证将已发送的206改为503。
单字节请求没有可提前交付的前缀，仍等待完整校验。
末块裁剪与跨块精确回退沿用相同规则，跨块冷填充也可提前交付前缀。

等待者只使用完整验证后的条目，不读取未完成共享缓冲。
加载者取消会释放源流、完整块缓冲、许可和守卫；由库唤醒等待者重新回源。
等待者取消不终止加载者。慢加载者不继续轮询时，填充也停止；
同键等待者可能受该慢消费者影响，服务HTTP层仍有逐次读取超时和媒体并发上限。
不宣称等待者可独立流式消费或慢客户端完全隔离。

流式候选减少了完整块前的**首个正文**依赖，不保证完整响应、首帧或单字节请求更快。
它仍会扩读同块未请求字节，并为完整缓存复制一份正文；
原始源块切片与缓存缓冲可能同时存活，最后字节可能额外形成一次正文产出。
网络分片较小时，轮询、复制调用和HTTP正文块数量也可能增加。
这些是接受的实验代偿，不将本地屏障验证作为CPU、RSS、功耗或生产延迟优势。
源码、冷热反例和验证边界见
`../../vedioServerRefer/problem-space/media-progressive-cache-evaluation.json`。
