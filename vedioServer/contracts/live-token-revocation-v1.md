# 直播执行端逐令牌撤权

版本v1，2026-11-07。适用Web、Android、iOS共同媒体契约；
当前仅回环实验，要求直播凭据和房间控制模式同时启用。

## 控制接口

可信控制服务向令牌绑定的媒体节点发送：

```text
POST /admin/room/revoke-token
Authorization: Bearer <internal-control-token>
Content-Type: application/json
```

```json
{
  "fence": {
    "cluster_id": "cluster",
    "tenant_id": "tenant",
    "room_id": "room",
    "target": {"node_id": "node-a", "incarnation": "current-start"},
    "revision": 3
  },
  "role": "subscriber",
  "token": "<live-token-to-revoke>"
}
```

内部控制凭据与用户JWT分开。拒绝Origin、重复Authorization、错误范围、
错误角色、错误启动代次、无效签名及过期令牌；正文和总期限沿用64KiB/8秒。
fence须完整匹配本节点和当前活动版本，已排空或旧版本不能写入新版本状态。
撤权不再查询协调多数派：它减少权限，不增加接入权限。

这里使用自有控制协议，不是RFC7009的公开OAuth撤权端点。
RFC7009的客户端认证、刷新令牌关联和用户会话策略没有由此实现。

## 执行语义

1. 现有jsonwebtoken/ring验证直播JWT，SHA256摘要已验证的header.payload签名输入。
   不保存JWT原文；签名编码的等价形式不会产生新的撤权身份。
2. 将摘要提交原媒体线程，先保存撤权记录，再删除所有当前使用该凭据的Rtc。
3. 发布者被删除时，沿用现有级联回收，清空本房间全部订阅和排队帧。
4. 处理完成后返回200与fence、revoked_tokens、removed_sessions，不返回令牌或摘要。

建连、续权和GET/HEAD/DELETE资源管理在执行命令时再次检查摘要及授权期限。
已经验签但仍在排队或读取正文的旧请求不能绕过后发生的撤权。
媒体数据路径不逐帧查询撤权表、不新增共识RPC、不运行后台撤权线程。

重复撤权同一有效凭据为200，removed_sessions为本次实际移除数，通常为0。
HTTP超时或连接中断表示结果未知，可携同一fence/令牌重新核对；
不自动创建会话，不将503当作“已撤权”。
验签时已过期为401，不能据此推断之前的控制命令是否执行。

| 状态 | 含义 |
| --- | --- |
| 200 | 处理时记录已保存，匹配会话已从媒体线程移除 |
| 401 | 控制身份或用户凭据无效；已撤令牌的后续媒体请求也为401 |
| 409 | 目标、启动代次或活动分配版本不匹配 |
| 503 | 媒体/验签预算不可用，或撤权记录已满；不得确认本次新撤权 |

## 范围、容量与迁移

撤销的是这一份已签授权，不是永久封禁主体，也不撤销发行者的刷新令牌。
若会话已用另一份更晚exp凭据续权，撤销旧凭据不删除新授权下的连接。
发行者独立核准的新凭据可以建新会话；禁止用户时，发行者必须同时停止再授权。

令牌本来就绑定节点、incarnation和assignment_revision，因此无需广播到所有节点：
其他节点拒绝其目标绑定；媒体重启后旧incarnation不匹配。
这个结论依赖所有媒体都执行相同范围检查、发行者不复制目标身份。
它不代表用户全设备退出、全域封禁或任意跨节点JWT撤销已经实现。

当前最多64条尚未失效的撤权记录，已失效记录按不可回退的授权时间水位回收，
见[回收与时间水位](revocation-reclamation-v1.md)。
容量压力不会淘汰尚未失效的记录。满额拒绝新增但允许重复已有有效撤权；
旧授权即使摘要已回收，仍会因时间水位而被拒绝。
64条是显式实验容量，不是生产规模或进程RSS上限。
尚未失效的记录只在房间版本永久排空后释放，因为旧版本此时已不能重新激活。
同进程重新激活同版本和普通发布者退出不能清除未失效记录，也不回退时间水位。
重启更换incarnation；新授权必须经外部身份与策略重新核准。

本轮已提供有界到期回收；后续生产仍需身份/撤权权威与容量实测，
不能直接把普通缓存的淘汰接到权限表。
大规模用户撤权、控制凭据轮换、TLS/mTLS、物理多机和原生仍待验收。
撤权确认不撤回已发数据或播放器缓存，不承诺屏幕零帧残留。
